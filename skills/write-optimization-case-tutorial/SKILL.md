# 優化案例教學（write-optimization-case-tutorial）

把一個實際遇到的問題整理成**一頁就能看懂**的 HTML 教學。重點是：**原因講清楚、解法講清楚、名詞看得懂**，其餘全部省略。

## 何時使用

- 要為「某個效能問題 / 常見錯誤 / 觀念陷阱」寫教學：卡頓、重複請求、記憶體洩漏、無效的 memo、參照比較……
- 要把既有的 `.md` 筆記改寫成這個格式。
- 不適用：純語法清單、面試題彙整、純概念定義（沒有「問題 → 原因 → 解法」結構的內容）。

## 檔案放哪裡

| 內容性質 | 路徑 |
|---|---|
| React 相關（memo、state、渲染） | `content/front-end/web/react/optimization-cases/` |
| JavaScript 語言 / 瀏覽器 API（Promise、防抖、記憶體、參照） | `content/front-end/javascript/optimization-cases/` |
| 其他領域 | 該領域資料夾下開 `optimization-cases/` |

- 檔名：小寫 kebab-case、`.html`，例如 `debounce-throttle.html`。
- **改寫既有 `.md` 時，新 HTML 完成並驗證後，直接刪除原 `.md`**（內容已由 HTML 取代，不留兩份）：
  - 整篇都被改寫 → 刪除整個 `.md` 檔。
  - 只有其中一段符合「問題 → 原因 → 解法」→ 只從 `.md` 移除那一段（可留一行指向新案例的說明），其餘內容保留，並順便修正其中的錯誤。
  - 多篇 `.md` 合併成一頁 → 每篇都依上面兩條處理。
- **原 `.md` 內有錯誤時**：錯誤要在新頁面以「更正」說明寫對；若 `.md` 還有保留的部分，也要直接把錯誤改正，不要留著錯的內容。
- 內容由 `src/app/HtmlNote.tsx` 以 iframe 渲染，所以頁面必須**自含**：不引用外部 CSS / JS / CDN、不用相對連結連到其他筆記。

## 起手式

1. 複製 `skills/write-optimization-case-tutorial/template.html`，替換 `{{TITLE}}`、`{{SUB}}`、`{{BODY}}`、`{{SCRIPT}}`（沒有互動示範就留空）。
2. 樣式（深淺色主題、各種元件）已在 template 裡，不要另外加。

## 頁面結構（固定順序）

1. **標題 + 副標**：`<h1>` 寫案例名；副標一句話，格式「症狀 · 結論：<黃色重點句>」。
2. **原因**（紅色 badge）：
   - 一條流程 `<div class="flow">` 表示因果鏈，每格不超過一行。
   - 一段「原本的寫法」程式碼，**錯的地方用紅色標出**。
   - 一個紅邊框 `box bad-box`，列 2–4 點成因，關鍵詞用 `<span class="bad">`。
3. **名詞**（綠色 badge）：每個初學者可能卡住的詞一張 `<div class="term">`。見下方規則。
4. **解法**（綠色 badge）：一個或多個，每個含「一句話說明（綠色重點）」+ 帶註解的程式碼；**對的地方用綠色標出**。
5. **判斷表**：什麼情況用哪個做法（表格或條列），可帶 `<span class="bad">不要</span>` 的反例。
6. **取捨 / 注意**（紅邊框 `box bad-box`，若有）：誠實寫出缺點與限制。

可選：**互動示範**（`<div class="demo">` + `{{SCRIPT}}`），只在「看數字 / 動畫比讀文字更快懂」時加，用原生 JS，不依賴外部資源。

## 顏色規則（語意固定，不要混用）

| 樣式 | 意義 | 用在 |
|---|---|---|
| `.bad` / `badge bad` / `bad-box` | 問題、錯誤、不要這樣做 | 原因、錯誤寫法、反例 |
| `.good` / `badge good` / `good-box` | 解法、正確做法 | 解法、正確寫法 |
| `.key` | 必看的關鍵句、取捨、注意 | 結論、限制、易錯點 |

- `<pre>` 內：`<span class="r">` 紅 = 問題處、`<span class="g">` 綠 = 解法處、`<span class="c">` 灰 = 註解。
- 一頁中**每種顏色只標真正的重點**，不要整段上色。

## 名詞卡片規則

- 凡是「沒學過會看不懂」的詞都要有卡片：技術名詞（如 IntersectionObserver）、容易誤解的詞（如參照、淺比較）、程式碼裡出現的陌生語法。
- 一張卡片 = **名稱 + 白話解釋 + 必要時一個比喻或一行範例**。
- 先講「它是什麼、為什麼這裡需要它」，再講細節；不要只給定義。
- 流程型的說明（例如 5 步驟）用 `<ol class="steps">`；需要畫面示意時用簡單的 CSS 方塊圖。

## 寫作規則

- **只寫原因與解法**。不寫背景故事、不寫「本文將介紹」、不重複同一件事。
- 句子短、用詞白話、繁體中文；技術名詞保留原文（React.memo、Promise.all）。
- 程式碼**每一行重要邏輯都加註解**，註解說「為什麼」而不是「做什麼」。
- **不要宣稱沒量測過的數字**。若原因是從程式結構推論的，要明說；互動示範的數字要標明是類比、依機器而異。
- **更正原筆記的錯誤**：改寫既有筆記時若發現不正確的內容（過時的 API、錯誤用法），在頁面用 `box bad-box` 的「更正」說明，並在回覆中告知使用者。
- 取捨一定要寫，不要讓讀者以為方案沒有代價。
