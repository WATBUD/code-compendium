優化案例：前端已經斷線，後端還在做昂貴的工作

使用者關頁或請求逾時，後端照樣跑完查詢並回 200 · 結論：讓工作跟著連線取消、加上逾時；有副作用的請求用 idempotency key 讓重試安全

原因

前端送出請求→ 後端開始跑昂貴查詢→ 前端關頁 / 逾時 / 取消→ 後端不知道，繼續跑完→ 回 200 但沒人收→ 前端以為失敗，重試又做一次 
// 原本：不管 client 還在不在，都把工作做完
app.post('/reports', async (req, res) => {
  const report = await buildReport(req.body)   // 沒有取消訊號、沒有逾時
  await db.saveReport(report)
  res.status(200).json(report)              // 寫出 200 ≠ 前端收到
})
  1. 前端斷線時，後端程式只有在主動監聽或讀寫連線時才會發現。沒監聽 → 斷線後仍佔著 CPU、DB 連線，白做工。
  2. 回 200 只代表「伺服器處理完，把回應交給作業系統送出」。TCP 的 ACK 也只代表封包到了對方的作業系統，不保證前端程式真的讀到。
  3. 前端沒收到回應通常會重試；如果是下單、扣款這類有副作用的請求，重試就會做兩次。
  4. 沒有逾時，一個很慢的請求可以無上限地佔著資源。

名詞 先看懂這幾個詞

TCP ACK 與「前端收到」的差別
TCP 會確認封包送到對方電腦（ACK），但那是作業系統層的確認。瀏覽器分頁可能在資料到達前就被關了，或拿到了卻沒處理。 後端沒有任何方式從一個 200 得知前端程式已經處理了回應。
FIN / RST
前端關閉連線時，作業系統會送出 FIN（正常結束）或 RST（強制中斷，例如還有沒讀完的資料）。 不論哪一種，後端程式要有在聽才會知道；不同框架用不同的方式把這件事通知你（下面的 context、close 事件）。 若中間有 proxy / load balancer，前端斷線後要等 proxy 也關掉它和後端的連線，後端才收得到。
取消訊號：Go 的 context.Context
Go 的 r.Context() 是這個請求的「取消開關」：client 斷線或 handler 結束時，它的 Done() 會被關閉。 把它一路傳給 DB 查詢、對外 HTTP 呼叫（QueryContext、NewRequestWithContext），它們就會在斷線時一起停下。 context.WithTimeout 再加上一個時間上限，兩個條件誰先到都會取消。
取消訊號：Node 的 AbortController / AbortSignal
AbortController 產生一個 signal，呼叫 controller.abort() 後，所有拿到這個 signal 的工作（fetch、支援 signal 的 driver、你自己的迴圈）都能停下。 AbortSignal.timeout(ms) 是時間到自動 abort 的 signal；AbortSignal.any([...]) 把多個 signal 合成一個（Node 20.3+）。
Node 偵測斷線：res 的 close 事件
res.on('close') 會在「回應送完」或「連線在送完前就斷了」時觸發，用 res.writableFinished 區分：還沒送完就 close = client 走了。 注意：新版 Node（16 以後）的 req.on('close') 在請求 body 讀完時就會觸發，不代表斷線；body 已經被讀完後才掛上的話甚至永遠不會觸發，所以要聽 res，不要聽 req。
冪等（idempotent）與 Idempotency-Key
冪等 = 同一個請求做 1 次和做 N 次，結果一樣。GET、PUT、DELETE 本來就該是冪等的；POST（下單、扣款）不是。 做法：前端為每一筆操作產生一個唯一 key，放在 Idempotency-Key 標頭，重試時沿用同一把 key。 後端第一次看到這把 key 才真的執行，之後看到同一把就直接回傳第一次的結果。 比喻：掛號單號碼 —— 同一張單拿去櫃台兩次，只會掛一次號。

解法 1 斷線就停：Go

把 r.Context() 加上逾時，一路傳到每個會花時間的呼叫

func reportHandler(w http.ResponseWriter, r *http.Request) {
	// client 斷線或超過 5 秒，兩者先到的那個會取消 ctx
	ctx, cancel := context.WithTimeout(r.Context(), 5*time.Second)
	defer cancel() // 提早結束時也釋放計時器

	report, err := buildReport(ctx, db)
	switch {
	case errors.Is(err, context.Canceled):
		return // client 已經走了，回什麼都沒人收，直接結束
	case errors.Is(err, context.DeadlineExceeded):
		http.Error(w, "report timed out", http.StatusServiceUnavailable)
		return
	case err != nil:
		http.Error(w, "internal error", http.StatusInternalServerError)
		return
	}
	w.Header().Set("Content-Type", "application/json")
	json.NewEncoder(w).Encode(report)
}

func buildReport(ctx context.Context, db *sql.DB) ([]Row, error) {
	// 傳入 ctx：取消時 driver 會中止這個查詢（是否真的停掉 DB 端的執行視 driver 而定）
	since := time.Now().AddDate(0, 0, -30)
	rows, err := db.QueryContext(ctx, "SELECT id, total FROM orders WHERE created_at > $1", since)
	if err != nil {
		return nil, err
	}
	defer rows.Close()

	var out []Row
	for rows.Next() {
		// 自己的 CPU 密集迴圈不會自動停，要主動檢查
		if err := ctx.Err(); err != nil {
			return nil, err
		}
		var row Row
		if err := rows.Scan(&row.ID, &row.Total); err != nil {
			return nil, err
		}
		out = append(out, enrich(row))
	}
	return out, rows.Err()
}

解法 1 斷線就停：Node

用 res 的 close 事件觸發 abort，並和逾時合併成一個 signal

import http from 'node:http'

http.createServer(async (req, res) => {
  const clientGone = new AbortController()
  // 回應還沒送完連線就關了 → client 斷線
  res.on('close', () => { if (!res.writableFinished) clientGone.abort() })
  // 斷線或 5 秒逾時，任一個發生就取消
  const signal = AbortSignal.any([clientGone.signal, AbortSignal.timeout(5000)])

  try {
    const report = await buildReport(signal)
    res.writeHead(200, { 'Content-Type': 'application/json' })
    res.end(JSON.stringify(report))
  } catch (err) {
    if (clientGone.signal.aborted) return            // 沒人在等了，不用回應
    if (err.name === 'TimeoutError') {
      res.writeHead(503).end('report timed out')
      return
    }
    res.writeHead(500).end('internal error')
  }
}).listen(3000)

async function buildReport(signal) {
  const rows = []
  for (let page = 0; page < 100; page++) {
    signal.throwIfAborted()                          // 每一輪開始前檢查，已取消就丟錯跳出
    // 支援 signal 的 API（fetch 等）直接傳進去，取消時連進行中的呼叫也會中止
    const r = await fetch(`http://127.0.0.1:4000/orders?page=${page}`, { signal })
    rows.push(...(await r.json()))
  }
  return rows
}

Express 也是同一個 res 物件，寫法相同。

解法 2 讓重試安全：Idempotency-Key

前端沒收到回應時，用同一把 key 重試；後端看到同一把 key 就回傳上次的結果，不再執行一次

// 前端：一筆操作產生一把 key，所有重試共用
const sleep = (ms) => new Promise((r) => setTimeout(r, ms))

async function createOrder(body) {
  const key = crypto.randomUUID()                                  // 在迴圈外產生：重試沿用同一把
  for (let attempt = 1; attempt <= 3; attempt++) {
    if (attempt > 1) await sleep(500 * 2 ** attempt)                  // 退避再試，避免一起打爆後端
    let res
    try {
      res = await fetch('/orders', {
        method: 'POST',
        headers: { 'Content-Type': 'application/json', 'Idempotency-Key': key },
        body: JSON.stringify(body),
        signal: AbortSignal.timeout(10_000),
      })
    } catch (err) {
      if (attempt === 3) throw err
      continue                                                          // 斷線 / 逾時 = 不知道後端有沒有做，帶同一把 key 重試是安全的
    }
    if (res.ok) return res.json()
    const retryable = res.status >= 500 || res.status === 409          // 4xx 是請求本身錯，重試也沒用
    if (!retryable || attempt === 3) throw new Error(`HTTP ${res.status}`)
  }
}
// 後端（Express 範例；store 可用 Redis 或 DB 的唯一索引）
app.post('/orders', async (req, res) => {
  const key = req.get('Idempotency-Key')
  if (!key) return res.status(400).json({ error: 'Idempotency-Key required' })

  // 原子地「搶」這把 key：Redis 用 SET key value NX EX 86400，DB 用唯一索引
  const claimed = await store.claim(key, { ttlSeconds: 86400 })
  if (!claimed) {
    const saved = await store.get(key)
    if (saved?.status === 'done') return res.status(saved.code).json(saved.body)  // 回傳第一次的結果
    return res.status(409).json({ error: 'request in progress' })                   // 第一次還在處理中
  }

  try {
    const order = await createOrderInTransaction(req.body)                          // 有副作用的部分包在交易裡
    await store.set(key, { status: 'done', code: 201, body: order })
    res.status(201).json(order)
  } catch (err) {
    await store.delete(key)                                                         // 失敗就釋放 key，讓之後的重試能再做
    res.status(500).json({ error: 'internal error' })
  }
})
兩個解法各管一半： 取消訊號讓沒人等的工作停下來（省資源）；idempotency key 讓沒收到回應的重試不會重複執行（正確性）。 idempotency key 也同時回答了「後端怎麼確定前端收到」——不用確定，前端沒收到就重試，拿到的是同一個結果。

判斷

情況做法
唯讀但昂貴（報表、搜尋、匯出）斷線就取消 + 逾時
有副作用（下單、扣款、寄信）交易 + Idempotency-Key；不要在寫入途中被斷線隨意中止，至少確保交易完整提交或完整回滾
工作要跑很久（幾十秒以上）改成回 202 Accepted + job id，前端輪詢或用 SSE 拿進度，不要讓 HTTP 請求一直掛著
想確定前端「真的收到」不要加「前端收到後再送一個 ACK 請求」，改用 idempotency key 讓重試安全
需要即時知道使用者在不在線（聊天、推播）WebSocket / SSE —— 那是另一個問題，不是用來確認回應有沒有收到

取捨 / 注意

  • 取消只對「有在檢查訊號」的程式碼有效：沒傳 ctx / signal 的函式、同步的 CPU 迴圈都不會自己停。
  • 「逾時就回錯誤」不等於「停止工作」：用 Promise.race 搶先回 503，背後的工作仍在跑；要把 signal 傳下去才真的停。
  • DB 端不一定停：client 取消查詢後，資料庫是否中止執行要看 driver 有沒有送出取消指令。
  • Idempotency key 有成本：要存結果、設過期時間、處理「第一次還在跑」的並發狀態（上面的 409）。key 過期後同一把 key 再來就會被當成新請求。
  • 中間有 proxy：前端斷線後，proxy 不一定立刻關掉到後端的連線，偵測會延遲。

更正 原筆記的問題

  1. 原筆記建議「前端收到回應後再送一個確認請求（ACK）」：多一次往返，而且這個 ACK 自己也可能遺失（那要不要再確認 ACK？），問題只是往後推。通常的做法是 idempotency key：不去確認前端收到，而是讓前端沒收到時可以安全重試。
  2. 原筆記建議用 WebSocket / SSE 偵測前端離線：這和本題無關。一般 HTTP 請求本身就能偵測斷線（Go 的 r.Context()、Node 的 res.on('close')）；長連線是拿來推播的，不能證明某個回應被處理了。
  3. 原筆記說「回應前前端關閉 → 後端仍會完成處理」，這是沒有監聽取消時才會發生的情況，正是要修的地方，不是必然結果。
  4. 原筆記的「超時機制」只寫了「5 秒未完成則取消」，沒說怎麼取消；必須把取消訊號傳進實際做事的程式碼，否則只是提早回錯誤，工作照跑。
