優化案例：錯的內容 push 到共用分支後的復原

把錯的 commit push（或 force push）到 release/staging · 結論：用 reflog 找回好的 commit，用 --force-with-lease 推回；別人可能已經 pull 就改用 git revert

原因

本地分支指到錯的 commit→ push 到共用分支→ 遠端分支也指到錯的 commit→ 隊友 pull / CI 部署拿到錯的內容 
# 情境：在共用分支上 merge 了還不該上的功能，然後 push
git switch release/staging
git merge feature/ABC-123                    # 這個功能還沒要上 staging
git push origin release/staging              # 錯的內容上了遠端

# 原筆記的復原方式
git reset --hard a1b2c3d
git push origin release/staging --force      # 不檢查遠端現況，直接覆蓋
  1. 分支只是一個「指向某個 commit 的指標」，push 會把遠端的指標也移到錯的 commit，之後誰 pull 都拿到錯的內容。
  2. 用 --force 推回時 git 不檢查遠端在這段時間有沒有新 commit，隊友剛推上去的東西會被默默蓋掉。
  3. 已經 pull 過錯內容的人，本地還留著那些 commit；遠端被改回去後，他下次 push 或 merge 可能又把錯的 commit 帶回來。

名詞 先看懂這幾個詞

reflog
本地 git 的「移動紀錄」：每次 commit、checkout、reset、merge、pull，HEAD 或分支指到哪裡都會記一筆。 所以就算分支已經被移走，原本那個好的 commit 還能從 reflog 找到。 
git reflog
# 9f8e7d6 HEAD@{0}: merge feature/ABC-123: Merge made by the 'ort' strategy.
# a1b2c3d HEAD@{1}: checkout: moving from feature/ABC-123 to release/staging   ← merge 之前的狀態
注意：reflog 只存在你自己的電腦，不會 push，也會過期（預設約 30～90 天）。
HEAD@{n}
「HEAD 在 n 次移動之前指到哪裡」。HEAD@{0} 是現在，HEAD@{1} 是上一步。可以直接拿來當 commit 用，但數字會隨每次操作改變，復原時建議抄下 commit hash。
git reflog show origin/release/staging
origin/release/staging 是你本地對遠端分支的「記憶」，每次 fetch / pull / push 都會更新，它也有自己的 reflog。 如果錯的 push 是別人做的，看這個可以知道你上次 fetch 時遠端指在哪。
救援分支
在動手 reset 之前，先開一個分支指向好的 commit：git branch rescue/staging-good a1b2c3d。 分支就是一個指標，開它幾乎不花成本，但能保證好的 commit 不會因為 reflog 過期或手誤而找不到。
git reset --hard <commit>
把目前的分支指標移到指定的 commit，並把工作目錄改成那個 commit 的樣子。 還沒 commit 的修改會直接消失，執行前先 git status 確認是乾淨的。
force push（--force）與 --force-with-lease
一般 push 只能「往前加 commit」。reset 之後本地比遠端「少」了 commit，一般 push 會被拒絕，所以要 force。
  • --force：不管遠端現在是什麼，直接蓋掉。
  • --force-with-lease：先確認遠端還是你上次看到的那個 commit才覆蓋；如果有人在你之後推了新東西，push 會失敗，不會蓋掉別人的 commit。
比喻：--force 是直接把別人的檔案存檔覆蓋；--force-with-lease 是「如果檔案還是我剛才打開的版本才存檔」。
git revert
不改寫歷史，而是新增一個「反向」的 commit，把指定 commit 的變更抵銷掉。 歷史只會往前加，一般 push 就能推上去，已經 pull 的人照常 pull 就好。 revert 一個 merge commit 時要加 -m 1，表示「以第 1 個 parent（merge 前的共用分支）為主線」。

解法 A 剛推、確定還沒人 pull：reset + --force-with-lease

先找好 commit、先釘住，再改指標，最後用 lease 推回

  1. 拿遠端最新狀態，確認錯的 commit 之後沒有別人的新 commit。
  2. 從 reflog 找出 push 錯之前的 commit。
  3. 開救援分支釘住它。
  4. 把共用分支 reset 回去。
  5. 用 --force-with-lease 推回，並通知隊友。
# 1. 看遠端現在指在哪，順便確認沒有別人在你之後推東西
git fetch origin
git log --oneline -5 origin/release/staging

# 2. 找出好的 commit（自己推錯：看 HEAD 的 reflog；別人推錯：看遠端追蹤分支的 reflog）
git reflog
git reflog show origin/release/staging

# 3. 先釘住好的 commit，之後怎麼操作都找得回來
git branch rescue/staging-good a1b2c3d

# 4. 確認工作目錄乾淨，再把共用分支指回好的 commit
git switch release/staging
git status
git reset --hard a1b2c3d

# 5. 遠端還是「錯的那個 commit」才覆蓋；有人在這之後推了東西就會被拒絕
git push --force-with-lease origin release/staging

# 更嚴格：直接寫出預期遠端現在的 commit（9f8e7d6 = 錯的那個）
git push --force-with-lease=release/staging:9f8e7d6 origin release/staging

# 也可以不動本地分支，直接把救援分支推到遠端的 release/staging
git push --force-with-lease origin rescue/staging-good:release/staging
推回後一定要通知隊友：說明哪個分支被改回哪個 commit。已經 pull 過錯內容的人，確認自己沒有要保留的本地修改後，執行： 
git fetch origin
git switch release/staging
git reset --hard origin/release/staging   # 丟掉本地那份錯的歷史，和遠端對齊
否則他們下次 push 可能把錯的 commit 再推回來。

解法 B 可能有人已經 pull / 已部署：git revert

不改寫歷史，新增一個抵銷的 commit，用一般 push 推上去

git switch release/staging
git pull --ff-only                          # 先和遠端對齊，避免 revert 在舊的基礎上

# 錯的是一個 merge commit：以第 1 個 parent（merge 前的 staging）為主線抵銷
git revert -m 1 9f8e7d6

# 錯的是一串一般 commit：抵銷 a1b2c3d 之後的全部（由新到舊逐一 revert）
git revert --no-edit a1b2c3d..HEAD

git push origin release/staging             # 一般 push 就好，不需要 force

判斷

情況做法
剛推，確定沒人 pull、CI 還沒部署reset + --force-with-lease，並通知隊友
可能已有人 pull、已部署，或分支有保護不能 force pushgit revert，一般 push
不確定有沒有人 pull選 git revert，它不會弄壞任何人的本地歷史
要覆蓋遠端分支不要用 --force，改用 --force-with-lease
好的 commit 只存在 reflog 裡先開救援分支釘住，再做任何 reset

取捨 / 注意

  • reset + force push：歷史乾淨，但改寫了共用歷史，每個已 pull 的人都要手動對齊。
  • --force-with-lease 的盲點：它比對的是 origin/release/staging。如果編輯器在背景自動 fetch，這個記憶會被更新成最新，保護就失效。要更保險就寫出預期的 commit（--force-with-lease=分支:commit）。
  • git revert：歷史會多出「加了又撤掉」的 commit。revert 過的 merge 之後要再 merge 同一個功能時，git 會認為那些 commit 已經 merge 過，需要先 revert 那個 revert commit，才能把功能帶回來。
  • reflog 只在本地：錯的 push 若是別人做的，你的 reflog 只記得你上次 fetch 時的狀態；更早的內容要請推錯的人從他的 reflog 找。

更正 原筆記的問題

  1. 原筆記用 git push ... --force 推回。應改用 --force-with-lease：遠端在這段時間若有人推了新 commit，--force 會直接蓋掉，--force-with-lease 會拒絕。
  2. 原筆記沒提到通知隊友。改寫共用分支後，已 pull 的人要 reset --hard origin/分支 對齊，否則錯的 commit 會被再推回來。
  3. 原筆記只給了改寫歷史一種做法。已經有人 pull 或分支禁止 force push 時，應該用 git revert。
