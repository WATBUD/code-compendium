優化案例：機密設定檔被 commit 後，從歷史中移除

金鑰檔 config/secrets.json 被 commit 並 push · 結論：先撤銷 / 更換金鑰，再用 git filter-repo 清掉歷史；清歷史不等於沒外洩

原因

commit config/secrets.json→ push 到遠端→ 每個 clone、fork、CI 都拿到一份→ git rm 只讓「之後的版本」沒有它 
git add config/secrets.json
git commit -m "add config"
git push origin main

# 發現後只做了這個
git rm config/secrets.json                   # 只從「新的」commit 移除
git commit -m "remove secret"
git push origin main

# 任何人仍然看得到舊版本
git log --all -p -- config/secrets.json
git show HEAD~1:config/secrets.json
  1. 每個 commit 都是完整快照，git rm 只新增一個「沒有這個檔案」的快照，舊的 commit 裡檔案還在。
  2. 一旦 push，金鑰就已經被複製到你控制不了的地方：別人的 clone、fork、CI log、代管平台的快取與 PR 參照。
  3. 所以改寫歷史只能防止「之後」有人從 repo 拿到它，不能把已經外洩的收回來。

名詞 先看懂這幾個詞

撤銷 / 輪替金鑰（revoke / rotate）
到發金鑰的地方（雲端主控台、API 後台）讓舊金鑰失效，換一把新的。 這是唯一真正止血的動作：舊金鑰失效後，就算有人已經拿到也沒用。要最先做，不要等歷史清完。
改寫歷史
commit 的 hash 是由「內容 + 上一個 commit 的 hash」算出來的。改掉某個舊 commit 的內容， 它和之後所有 commit 的 hash 都會變，等於產生一份新的歷史。所以推回遠端必須 force push，所有協作者也都要換成新歷史。
git filter-repo
官方推薦、用來取代舊的 git filter-branch 的改寫歷史工具（需另外安裝：pip install git-filter-repo 或 brew install git-filter-repo）。 它會一次掃過所有分支和 tag 的每個 commit，套用你的規則後重建歷史，結束時自動清掉 reflog 並做垃圾回收，舊物件不會留在本地。
--path <檔案> --invert-paths
--path 是「只保留這個路徑」；加上 --invert-paths 反過來變成「保留除了這個路徑以外的全部」，也就是從所有歷史中刪掉它。 檔案若曾改名或搬過位置，每個舊路徑都要列出來。
為什麼 filter-repo 會移除 origin
改寫後的 repo 和原本的遠端已經是兩份不同的歷史。filter-repo 刻意把 origin remote 刪掉，避免你在還沒確認結果前就不小心推上去。確認沒問題後，自己 git remote add origin ... 加回來。
git push origin --force --all / --tags
git push <remote> ... 的第一個參數是 remote 的名字（通常是 origin），不是分支名。 --all 推所有本地分支、--tags 推所有 tag，兩者不能寫在同一個指令裡，所以分兩次。

解法 先止血，再清歷史，最後讓所有人換新歷史

順序：撤銷金鑰 → 新 clone → filter-repo → 檢查 → 加回 origin → force push → 協作者重新 clone

  1. 立刻撤銷 / 更換金鑰，並檢查這段時間有沒有被濫用的紀錄。
  2. 在一份全新的 clone 上操作（filter-repo 預設只接受新 clone，避免弄壞有本地修改的 repo）。
  3. 用 filter-repo 從所有歷史刪除檔案，並確認真的清乾淨。
  4. 加回 origin，force push 所有分支和 tag。
  5. 通知協作者重新 clone，並把檔案加進 .gitignore。
# 1. 先到金鑰的發行方撤銷舊金鑰、換新的（這一步不在 git 裡）

# 2. 全新 clone（filter-repo 會把 origin/* 遠端分支都一起處理）
git clone git@github.com:you/repo.git repo-clean
cd repo-clean

# 3. 從所有分支、tag 的歷史中刪掉這個檔案
git filter-repo --path config/secrets.json --invert-paths

#    確認清乾淨：這兩行都不該有任何輸出
git log --all --oneline -- config/secrets.json
git grep -I "這裡放金鑰的一小段特徵字串" $(git rev-list --all)

# 4. filter-repo 刻意移除了 origin，確認無誤後再加回來
git remote add origin git@github.com:you/repo.git
git push origin --force --all      # remote 名稱是 origin，不是分支名
git push origin --force --tags

# 5. 防止再犯
echo "config/secrets.json" >> .gitignore
git add .gitignore
git commit -m "ignore local secrets"
git push origin main
協作者怎麼處理：刪掉舊的 clone，重新 clone。 只在舊 clone 裡 git reset --hard origin/main 不夠：其他本地分支、stash、reflog 仍然帶著舊歷史，之後一 push 或 merge 就可能把檔案帶回遠端。 還沒 push 的修改，先在舊 clone 用 git format-patch 匯出，再到新 clone 用 git am 套用。

判斷

情況做法
金鑰已經 push 過（不論多久）先撤銷 / 更換金鑰，再考慮清歷史
只 commit、還沒 push直接 git reset --soft HEAD~1 或 git commit --amend 移除即可，不用 filter-repo（仍建議換金鑰）
整個檔案都不該進 repo--path <檔案> --invert-paths
檔案要保留，只是裡面有一段金鑰git filter-repo --replace-text 規則檔，把那段字串換成 ***REMOVED***
以為清了歷史就安全不要：歷史改寫收不回已外洩的副本
還在用 git filter-branch 的教學不要照抄它的清理步驟（例如 .git/refs/original/），filter-repo 不需要

取捨 / 注意

  • 所有 commit hash 都會改變：開著的 PR、文件裡的 commit 連結、別人基於舊歷史的分支都會對不上。
  • 代管平台可能還留著舊 commit：例如 PR 的參照（refs/pull/*）是唯讀的，force push 蓋不掉，舊 commit 仍可能透過 hash 被看到；要清除需聯絡平台客服。已經存在的 fork 你也刪不掉。
  • 受保護分支可能禁止 force push，要先暫時解除保護，推完再設回去。
  • 這些都是撤銷金鑰才是第一步的原因：清歷史只降低之後被翻出來的機會。

更正 原筆記的問題

git filter-repo --path config/secrets.json --invert-paths
git remote add origin git@github.com:you/repo.git
rm -rf .git/refs/original/                # filter-branch 的殘留步驟，filter-repo 不會產生這個資料夾
git reflog expire --expire=now --all       # filter-repo 已經做過，多跑無害但不需要
git gc --prune=now --aggressive            # 同上
git push main --force --all              # main 會被當成 remote 名稱 → 應為 origin
git push main --force --tags
# 協作者：
git fetch origin
git reset --hard origin/main               # 只對齊目前分支，其他本地分支仍帶舊歷史
  1. 最重要：原筆記沒有撤銷 / 更換金鑰。金鑰 push 出去的那一刻就已外洩（clone、fork、CI log、平台快取、PR 參照），改寫歷史收不回來，必須先讓舊金鑰失效。
  2. git push main --force --all：第一個參數是 remote 名稱，main 不是 remote，指令會失敗。應為 git push origin --force --all（tag 同理）。
  3. rm -rf .git/refs/original/ 是 git filter-branch 的清理步驟；filter-repo 不會建立這個資料夾，而且結束時已經自動做了 reflog expire 和 gc。
  4. 原筆記說「需要重新設置 origin」但沒說原因：filter-repo 刻意移除 origin，防止還沒檢查就推上去。應在檢查結果之後再加回。
  5. 協作者只 reset --hard origin/main 不夠，應重新 clone，否則其他分支會把舊歷史帶回來。
