資料庫優化案例：沒有索引的 WHERE → 全表掃描

WHERE 條件一查就慢，資料越多越慢 · 結論：為「常用、選擇性高」的查詢欄位建非叢集索引，讓查詢從逐行掃描變成 B+ 樹定位

原因

WHERE OrderName = …→OrderName 沒有索引→只能從第一列讀到最後一列→時間跟資料量成正比

原本的寫法（以 SQL Server 語法為例）：

CREATE TABLE Orders (
    OrderID   INT PRIMARY KEY,   -- SQL Server 預設會在主鍵建「叢集索引」
    OrderName NVARCHAR(100),     -- 沒有索引
    OrderDate DATE
);

SELECT *
FROM Orders
WHERE OrderName = N'Widget A';   -- 只能 Full Table Scan
  1. 資料在磁碟上是照 OrderID（叢集索引鍵）排序的，OrderName 是亂序的，資料庫不知道 'Widget A' 在哪裡。
  2. 只好每一列都讀出來比對（全表掃描），即使只有 2 列符合，也要看完全部。
  3. 資料量小時感覺不出來，資料一多，讀取量跟著線性成長；表越大越慢、也越佔 I/O 與記憶體。
-- 全表掃描：一列一列看
[Row 1] → [Row 2] → [Row 3] → … → [Row N]   -- 讀 N 列

名詞 先看懂這幾個詞

全表掃描（Full Table Scan / Clustered Index Scan）
沒有可用的索引時，資料庫把整張表讀過一遍。SQL Server 的執行計畫裡會顯示為 Table Scan（沒有叢集索引的表）或 Clustered Index Scan。
叢集索引（Clustered Index）
資料本身就照這個鍵排序存放，一張表只能有一個。比喻：圖書館的書照 ISBN 排在書架上。
非叢集索引（Nonclustered Index）
另外存一份「排好序的欄位值 + 指向資料列的位置」，資料本身不動。比喻：照書名排序的卡片目錄，每張卡寫著書在哪個書架。
B+ 樹
索引用的資料結構。特點：
  • 所有資料都在最底層的葉節點，上層節點只放「導航用的分隔鍵」。
  • 葉節點彼此串成一條鏈，找到第一個 'Widget A' 後往右讀就能拿到下一個，很適合範圍查詢。
  • 每個節點能放很多鍵，所以樹很矮：幾百萬列通常也只要 3–4 層，查一次只讀幾個頁面。
              [ Gadget | Widget ]              ← 根：只放分隔鍵
             /         |         \
 [Apple, Bolt] ⇄ [Gadget B, Lamp] ⇄ [Widget A, Widget A, Widget C]
                                        ↑ 葉節點：存全部鍵 + 指向資料列，彼此串接
分裂（split）時的差別
節點放滿時要分成兩半。假設葉節點最多 3 個鍵，已有 [Alice, Bob, Charlie]，再插入 David： 
-- B+ 樹（葉節點分裂）：中間鍵「複製」到上層，右邊葉節點保留它
        [Charlie]
       /         \
[Alice, Bob] ⇄ [Charlie, David]

-- B 樹：中間鍵「搬」到上層，葉節點不再有它
        [Charlie]
       /         \
[Alice, Bob]   [David]
B+ 樹的資料一定都在葉節點，所以 Charlie 必須留在葉節點裡。
Index Seek
從 B+ 樹的根一路往下比較、直接走到目標葉節點。讀取量約等於「樹的層數 + 符合的列數」，而不是整張表。
行定位器（Row Locator）與 Key Lookup
非叢集索引的葉節點只有索引欄位 + 一個「去哪裡找完整資料」的指標：
  • 表有叢集索引 → 指標是叢集索引鍵（這裡是 OrderID），回表叫 Key Lookup。
  • 表沒有叢集索引（heap）→ 指標是實體位置 RID，回表叫 RID Lookup。
SELECT * 要的欄位不在索引裡，所以每一筆符合的列都要回表一次。
選擇性（Selectivity）
一個條件能篩掉多少資料。OrderName = 'Widget A' 只命中少數列 → 選擇性高，索引很有用；Status = 'Done' 命中 80% → 選擇性低，用索引反而比直接掃描還慢。
覆蓋索引（Covering Index）/ INCLUDE
把查詢需要的其他欄位也「附」在索引葉節點上（INCLUDE），查詢只看索引就夠了，不用回表。

解法 建非叢集索引，讓查詢走 Index Seek

為 WHERE 常用、選擇性高的欄位建索引：

CREATE NONCLUSTERED INDEX IX_Orders_OrderName
    ON Orders (OrderName);          -- 依 OrderName 排序的 B+ 樹

SELECT *
FROM Orders
WHERE OrderName = N'Widget A';       -- Index Seek 找到葉節點 → 每筆再 Key Lookup 取其他欄位

更好：只取需要的欄位，並用 INCLUDE 讓索引「覆蓋」查詢：

CREATE NONCLUSTERED INDEX IX_Orders_OrderName_Cover
    ON Orders (OrderName)
    INCLUDE (OrderDate);           -- OrderDate 只存在葉節點，不參與排序

SELECT OrderID, OrderDate            -- OrderID 是叢集鍵，本來就在非叢集索引裡
FROM Orders
WHERE OrderName = N'Widget A';       -- 只需 Index Seek，不用回表
  1. 從根節點開始，依排序規則（collation）比較 'Widget A' 和分隔鍵，決定往哪個子節點走。
  2. 重複到葉節點，找到第一個 'Widget A'。
  3. 沿著葉節點的鏈往右讀，直到值不再是 'Widget A'。
  4. 需要索引裡沒有的欄位時，用行定位器回表取資料（Key Lookup）；用了覆蓋索引就省掉這步。

示範 讀取量的差別（類比）

　

-
全表掃描：要讀的列數
-
B+ 樹層數（每節點 ≈ 300 鍵）
-
Seek：層數 + 每筆回表一次

只是用公式估算的「讀取次數」類比，不是實測時間；實際成本依頁面大小、快取、硬碟而異。符合的列很多時，回表次數會追上掃描，這就是優化器有時仍選擇掃描的原因。

判斷 這個欄位該不該建索引？

情況建議
常出現在 WHERE / JOIN / ORDER BY、命中少數列（名稱、Email、外鍵）建非叢集索引
查詢只需要少數幾個欄位INCLUDE 做成覆蓋索引，避免 Key Lookup
多個條件一起查（WHERE CustomerID = ? AND OrderDate >= ?）複合索引，等值條件的欄位放前面
低選擇性欄位（狀態、性別、布林）單獨建索引不要：命中太多列，優化器通常仍會掃描；可放進複合索引，或只對少數值建篩選索引（filtered index）
長文字欄位（描述、備註），查詢用 LIKE '%關鍵字%'不要：開頭是萬用字元無法 Seek，索引又大又沒用；需要時改用全文檢索（Full-Text Index）
對欄位套函式：WHERE YEAR(OrderDate) = 2024不要這樣寫，索引用不上；改成範圍 OrderDate >= '2024-01-01' AND OrderDate < '2025-01-01'
寫入很頻繁、幾乎不查詢的表（例如 log）少建索引，每個索引都會拖慢寫入

取捨 注意

  • 索引會拖慢寫入：每次 INSERT / UPDATE / DELETE，所有相關索引都要一起更新，還可能造成頁面分裂。
  • 索引佔空間：每個非叢集索引都是另一份排序好的資料（加上 INCLUDE 的欄位）。
  • SELECT * + 非叢集索引 = 每筆都 Key Lookup。符合的列一多，回表的隨機讀取比直接掃描還貴，優化器會自動改回掃描，看起來像「索引沒作用」。
  • 要確認索引真的被用到：看實際執行計畫（Index Seek vs. Scan），不要只憑感覺。
更正原筆記：
  • 原筆記的分裂圖 [Charlie] → [Alice, Bob] [David] 是 B 樹的行為。B+ 樹的葉節點分裂時，中間鍵是複製到上層，右邊葉節點仍保留它：[Alice, Bob] ⇄ [Charlie, David]。
  • 原筆記的範例樹 [M] → [G] [T] → [A-E][F-L][N-R][S-Z] 結構不成立：只有一個鍵的節點只會有兩個子節點，畫成三個也對不上鍵的範圍。上方已改成正確的小例子。
  • 字串比較不是比「第一個字的 ASCII 碼」，而是依資料庫的排序規則（collation）整串比較，例如 SQL Server 預設不分大小寫。
  • 「行定位器（Row Identifier）」只適用於沒有叢集索引的表（RID）。這個例子的 Orders 有主鍵叢集索引，定位器其實是 OrderID，回表是 Key Lookup。
  • 原筆記另一篇建議為「描述、備註」等長文字欄位和「類別、狀態」等低選擇性欄位建非叢集索引，這通常沒有效果，理由見上方判斷表。
