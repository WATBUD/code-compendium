Go 優化案例：Goroutine 洩漏 → 用 context 取消

啟動的 goroutine 永遠不會結束，數量越積越多 · 結論：每個 goroutine 都要有「什麼時候停」的訊號，並在 select 裡監聽它

原因

go func() { for { … } }()→迴圈裡沒有任何結束條件→呼叫端不需要它了也停不下來→goroutine 越積越多（洩漏）

原本的寫法：每次請求都啟動一個輪詢 goroutine，但從來沒有關掉它。

func startPolling() {
    go func() {
        for {                              // 沒有退出條件
            fmt.Println("polling...")
            time.Sleep(500 * time.Millisecond)
        }
    }()
}

func handleRequest() {
    startPolling() // 請求結束了，goroutine 還在跑；呼叫 1000 次就留下 1000 個
}
  1. Go 沒有辦法從外部「殺掉」一個 goroutine，它只能自己 return。
  2. 迴圈裡沒有檢查任何停止訊號，所以它會一直跑到整個程式結束。
  3. 每個 goroutine 都佔記憶體（堆疊至少數 KB），還抓著它引用到的變數，GC 也收不回來。
  4. 另一種常見洩漏：goroutine 卡在送 / 收 channel，對方已經不在了，它就永遠等下去。

名詞 先看懂這幾個詞

goroutine 洩漏
不再需要、卻永遠不會結束的 goroutine。和記憶體洩漏一樣，單一個看不出問題，累積起來就會吃光記憶體。可以用 runtime.NumGoroutine() 或 pprof 的 goroutine profile 觀察數量是否一直上升。
context.Context
Go 標準的「取消訊號 + 期限」傳遞工具。呼叫端持有 cancel，被呼叫的 goroutine 監聽 ctx.Done()。父 context 取消時，所有從它衍生的子 context 也會一起取消。
ctx.Done()
回傳一個 channel，context 被取消或逾時時，這個 channel 會被關閉。關閉的 channel 可以被任何人立刻讀到，所以多個 goroutine 都能同時收到訊號。ctx.Err() 會告訴你原因：context.Canceled 或 context.DeadlineExceeded。
WithCancel / WithTimeout / WithDeadline
  • WithCancel(parent)：手動呼叫 cancel() 才取消。
  • WithTimeout(parent, 2*time.Second)：過了一段時間自動取消。
  • WithDeadline(parent, t)：到了某個時間點自動取消（WithTimeout 就是 WithDeadline(parent, time.Now().Add(d))）。
三者都回傳 cancel，就算會自動逾時，也要 defer cancel() 釋放計時器等資源。
select
同時等待多個 channel，哪個先準備好就執行哪個。沒有 default 時會阻塞等待（不吃 CPU）；有 default 時，所有 case 都沒準備好就立刻執行 default。
time.Ticker
每隔固定時間往 ticker.C 送一次訊號。用它取代迴圈裡的 time.Sleep，就能把「等下一輪」和「等取消」放進同一個 select。用完要 ticker.Stop()。
sync.WaitGroup
等一組 goroutine 全部結束：啟動前 wg.Add(1)，goroutine 結束時 wg.Done()，主程式 wg.Wait() 會阻塞到計數歸零。比「time.Sleep 一下希望它結束了」可靠。

解法 1 context.WithCancel + select 監聽 ctx.Done()

goroutine 在 select 裡同時等「下一輪」和「取消」，取消時立刻 return：

package main

import (
    "context"
    "fmt"
    "sync"
    "time"
)

func poll(ctx context.Context, wg *sync.WaitGroup) {
    defer wg.Done()                              // 不管怎麼離開，都通知 WaitGroup
    ticker := time.NewTicker(500 * time.Millisecond)
    defer ticker.Stop()                          // 釋放 ticker

    for {
        select {
        case <-ctx.Done():                       // 取消訊號一到，馬上結束
            fmt.Println("poll stopped:", ctx.Err())
            return
        case <-ticker.C:                         // 沒取消時，每 500ms 做一次
            fmt.Println("polling...")
        }
    }
}

func main() {
    ctx, cancel := context.WithCancel(context.Background())
    var wg sync.WaitGroup

    wg.Add(1)                                    // 要在 go 之前 Add，避免 Wait 先跑完
    go poll(ctx, &wg)

    time.Sleep(2 * time.Second)                  // 模擬「呼叫端做了一陣子事」
    cancel()                                     // 發出取消訊號
    wg.Wait()                                    // 確實等到 goroutine 結束
    fmt.Println("main exits")
}

解法 2 context.WithTimeout：時間到自動停

func main() {
    ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
    defer cancel()                               // 提早結束時也釋放資源

    var wg sync.WaitGroup
    wg.Add(1)
    go poll(ctx, &wg)                            // 同一個 poll，2 秒後 ctx.Err() = DeadlineExceeded
    wg.Wait()
    fmt.Println("main exits")
}

解法 3 不用 context：close(stop) 廣播停止

func poll(stop <-chan struct{}, wg *sync.WaitGroup) {
    defer wg.Done()
    ticker := time.NewTicker(500 * time.Millisecond)
    defer ticker.Stop()
    for {
        select {
        case <-stop:                             // channel 被 close 後，這裡立刻可讀
            return
        case <-ticker.C:
            fmt.Println("polling...")
        }
    }
}

// 呼叫端
stop := make(chan struct{})
var wg sync.WaitGroup
wg.Add(1)
go poll(stop, &wg)
close(stop)                                      // 用 close 而不是送值：所有監聽者都會收到
wg.Wait()

補充 卡在 channel 的洩漏也要監聽取消

func produce(ctx context.Context, out chan<- int) {
    for i := 0; ; i++ {
        select {
        case out <- i:                           // 對方還在收：正常送出
        case <-ctx.Done():                       // 對方不收了：不要永遠卡在送出
            return
        }
    }
}

判斷 用哪一種

情況做法
由呼叫端決定何時停（使用者離開、服務關閉）context.WithCancel
限制最長執行時間（HTTP 請求、DB 查詢）context.WithTimeout
要在某個固定時間點前結束context.WithDeadline
程式內部的小工具、不需要往下傳期限close(stop) + select
HTTP handler 裡啟動的工作直接用 r.Context()，用戶端斷線時會自動取消
等 goroutine 結束sync.WaitGroup；不要用 time.Sleep 猜時間
select 裡放 default: + time.Sleep 輪詢不要，改成監聽 ctx.Done() + ticker / timer

取捨 注意

  • 取消是「請求」不是「強制」：goroutine 只有在檢查 ctx.Done() 時才會停。如果它正在做一個不看 ctx 的長時間運算 / 阻塞呼叫，要等那一步做完。所以底層函式也要接收並傳遞 ctx（例如 http.NewRequestWithContext、db.QueryContext）。
  • ctx 慣例放在函式第一個參數，不要存進 struct 長期保存。
  • 忘了呼叫 cancel 本身也是洩漏：子 context 會一直掛在父 context 上，直到父 context 結束；go vet 會對沒用到的 cancel 發出警告。
  • 只把 poll 包成「接收 ctx」不夠，啟動它的人也要負責取消，否則還是會洩漏。
更正原筆記：
  • 原範例在 select 用 default: + time.Sleep(500ms)：goroutine 大部分時間在 Sleep，不會看到取消訊號，最多要延遲一整個 Sleep 才停。如果把 Sleep 拿掉（或工作很快），default 會變成空轉迴圈，吃滿一顆 CPU。正確做法是把等待也放進 select：case <-ctx.Done() + case <-ticker.C（或 time.After）。
  • 原範例在 cancel() 後用 time.Sleep(1 * time.Second)「確保 worker 有時間結束」，這只是猜時間，不保證它真的結束了；應改用 sync.WaitGroup。
  • 原筆記列出的輸出（固定 4 行 running）不一定成立：2 秒、每 500ms 一次，邊界時間點會有競爭，可能印 4 或 5 行。
