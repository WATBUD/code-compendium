RabbitMQ 優化案例：訊息遺失（重啟 / 消費者當掉）

RabbitMQ 重啟或消費者當掉，訊息就不見了 · 結論：佇列 durable + 訊息 Persistent + 手動 Ack + Publisher Confirms，四個缺一不可

原因

佇列非 durable、訊息非持久→只存在記憶體→Broker 重啟 → 佇列和訊息一起消失
autoAck = true→送出就算「已處理」並刪除→消費者處理到一半當掉 → 訊息遺失

原本的寫法（生產者 + 消費者）：

q, err := ch.QueueDeclare(
    "hello",
    false, // durable：佇列定義只在記憶體，重啟就沒了
    false, false, false, nil,
)

err = ch.Publish("", q.Name, false, false, amqp.Publishing{
    ContentType: "text/plain",
    Body:        []byte(body),
    // 沒有 DeliveryMode → 預設是 Transient（非持久）訊息
})

msgs, err := ch.Consume(
    q.Name, "",
    true, // autoAck：訊息一送到消費者就從佇列刪除
    false, false, false, nil,
)
for msg := range msgs {
    handle(msg.Body) // 這裡當掉 → 訊息已被刪除，找不回來
}
  1. durable = false：佇列本身在重啟後消失，裡面的訊息當然也跟著消失。
  2. 沒設 DeliveryMode: Persistent：就算佇列是 durable，非持久訊息重啟後仍會被丟掉。
  3. autoAck = true：Broker 一把訊息送出就刪除，不管消費者有沒有處理完。
  4. 沒有 Publisher Confirms：Publish 回傳沒有 error 只代表「送出去了」，不代表 Broker 已收到、已寫入磁碟。

名詞 先看懂這幾個詞

Broker
RabbitMQ 伺服器本身。生產者把訊息交給它，它放進佇列（Queue），再送給消費者。就像郵局：寄件人、郵局、收件人。
durable（持久化佇列）
宣告佇列時的第二個參數。durable 的佇列定義會存到磁碟，Broker 重啟後佇列還在。注意：它只保證「佇列」還在，不保證「裡面的訊息」還在。
DeliveryMode: Persistent（持久化訊息）
每一則訊息自己的屬性。amqp.Persistent（值為 2）表示這則訊息要寫入磁碟；預設 Transient（1）只放記憶體。必須「durable 佇列 + Persistent 訊息」兩個都設，重啟後訊息才會留下。
Ack（確認，acknowledgement）
消費者告訴 Broker「這則我處理完了，可以刪了」。
  • autoAck = true：送出即刪，最快但最危險。
  • 手動 Ack：處理完才呼叫 d.Ack(false)。若消費者在 Ack 前斷線，Broker 會把訊息重新排回佇列交給別人。
  • Nack(false, requeue)：告訴 Broker 處理失敗，requeue=true 排回佇列、false 丟棄或送到死信佇列（若有設定）。
Publisher Confirms（發布確認）
Ack 的反方向：Broker 告訴生產者「這則我收到了」。對「持久訊息 + durable 佇列」，Broker 會在寫入磁碟後才回確認。開啟方式是 ch.Confirm(false)，之後每次發布都能等確認。
Qos / prefetch
ch.Qos(10, 0, false) 表示「同一個消費者手上最多 10 則還沒 Ack 的訊息」。不設的話 Broker 會把整個佇列一口氣推給消費者，撐爆記憶體、也讓其他消費者分不到工作。它不是防遺失的設定，但手動 Ack 時一定要搭配。
at-least-once（至少一次）
手動 Ack 的代價：消費者處理完但還沒來得及 Ack 就當掉，這則訊息會被重送，同一則可能被處理兩次。所以處理邏輯要能「重複執行也沒關係」（冪等，idempotent），例如用訊息 ID 去重。

解法 四件事一起做

安裝目前維護中的官方 Go 客戶端：

go get github.com/rabbitmq/amqp091-go

生產者：durable 佇列 + Persistent 訊息 + Publisher Confirms

package main

import (
    "context"
    "log"
    "time"

    amqp "github.com/rabbitmq/amqp091-go"
)

func main() {
    conn, err := amqp.Dial("amqp://guest:guest@localhost:5672/") // 本機預設帳號，正式環境請換掉
    if err != nil {
        log.Fatal(err)
    }
    defer conn.Close()

    ch, err := conn.Channel()
    if err != nil {
        log.Fatal(err)
    }
    defer ch.Close()

    q, err := ch.QueueDeclare(
        "task_queue",
        true,  // durable：重啟後佇列還在
        false, // autoDelete
        false, // exclusive
        false, // noWait
        nil,   // args
    )
    if err != nil {
        log.Fatal(err)
    }

    if err := ch.Confirm(false); err != nil { // 開啟 Publisher Confirms
        log.Fatal(err)
    }

    ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
    defer cancel()

    dc, err := ch.PublishWithDeferredConfirmWithContext(ctx,
        "",     // exchange：空字串 = 預設 exchange
        q.Name, // routing key：預設 exchange 直接用佇列名
        false,  // mandatory
        false,  // immediate
        amqp.Publishing{
            DeliveryMode: amqp.Persistent, // 訊息寫入磁碟
            ContentType:  "text/plain",
            Body:         []byte("Hello RabbitMQ!"),
        },
    )
    if err != nil {
        log.Fatal(err)
    }

    // 等 Broker 回確認：true = 已收下（持久訊息 = 已寫入磁碟）
    ok, err := dc.WaitContext(ctx)
    if err != nil || !ok {
        log.Fatalf("沒有被 Broker 確認，需要重送: ok=%v err=%v", ok, err)
    }
    log.Println("已確認送達")
}

消費者：手動 Ack + Qos

package main

import (
    "log"

    amqp "github.com/rabbitmq/amqp091-go"
)

func handle(body []byte) error {
    log.Printf("處理: %s", body) // 實際業務邏輯；要能承受重複執行
    return nil
}

func main() {
    conn, err := amqp.Dial("amqp://guest:guest@localhost:5672/")
    if err != nil {
        log.Fatal(err)
    }
    defer conn.Close()

    ch, err := conn.Channel()
    if err != nil {
        log.Fatal(err)
    }
    defer ch.Close()

    // 宣告參數要和生產者完全一致，否則會被 Broker 拒絕
    q, err := ch.QueueDeclare("task_queue", true, false, false, false, nil)
    if err != nil {
        log.Fatal(err)
    }

    if err := ch.Qos(10, 0, false); err != nil { // 手上最多 10 則未 Ack
        log.Fatal(err)
    }

    msgs, err := ch.Consume(
        q.Name,
        "",    // consumer tag：空字串由 Broker 產生
        false, // autoAck = false：處理完才 Ack
        false, // exclusive
        false, // noLocal
        false, // noWait
        nil,   // args
    )
    if err != nil {
        log.Fatal(err)
    }

    for d := range msgs {
        if err := handle(d.Body); err != nil {
            d.Nack(false, true) // 失敗：排回佇列（小心無限重試，正式環境常改送死信佇列）
            continue
        }
        d.Ack(false) // 成功才確認；Ack 前當掉 → Broker 會重送
    }
}

判斷 哪個設定防哪種遺失

情境沒設定時要做的
Broker 重啟佇列消失QueueDeclare durable = true
Broker 重啟佇列在，但訊息消失DeliveryMode: amqp.Persistent
消費者處理到一半當掉訊息已被刪除autoAck = false + 處理完 d.Ack(false)
訊息送出後、寫入磁碟前 Broker 當掉 / 網路斷線生產者以為送成功ch.Confirm + 等待確認，沒確認就重送
消費者一次被塞太多訊息記憶體爆、分配不均ch.Qos(prefetch, 0, false)
只是暫時性、可丟的訊息（例如即時通知）—可以刻意不持久化換效能，但要是有意識的選擇

取捨 注意

  • 持久化要寫磁碟：吞吐量會比純記憶體低，等待 Confirm 也會增加延遲。大量發送時不要每則都同步等，可以批次發送後再一起等確認。
  • 手動 Ack = 至少一次：會有重複訊息，消費端要能冪等。
  • 已經存在的非 durable 佇列不能直接改成 durable：用同名但不同參數再宣告一次，Broker 會回錯誤（PRECONDITION_FAILED）並關閉 channel。要先刪掉舊佇列或換新名字。
  • 單機 durable 只防「重啟」，不防「整台機器 / 硬碟壞掉」。需要高可用時改用多節點複製的 quorum queue（宣告時帶 x-queue-type: quorum）。
