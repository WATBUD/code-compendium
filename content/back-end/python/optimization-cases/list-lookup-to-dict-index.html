Python 優化案例：在 list 裡逐一找物件 → 改用 dict 索引

用 list 依屬性找物件，資料一多就變慢 · 結論：需要「依 key 反覆查找」時，先建一次 dict 索引，之後每次查找平均 O(1)

原因

依 id 找物件→list 只能從頭比到尾（O(n)）→在迴圈裡又找 m 次→總共約 n × m 次比較

原本的寫法：

def find_user(users, user_id):
    for u in users:                  # 每次都從第一個開始比
        if u.id == user_id:
            return u
    return None

for order in orders:                  # m 筆訂單
    user = find_user(users, order.user_id)   # 每筆都掃一次 n 個使用者
    ...
  1. list 只能用位置（index）快速存取；要依「內容 / 屬性」找，就只能逐一比較，平均要看一半、找不到時要看全部。
  2. 單次查找看不出問題，但放進迴圈裡，成本是 n × m：使用者和訂單各多 10 倍，比較次數就多 100 倍（這是從程式結構推算，不是實測）。
  3. x in my_list、my_list.remove(x)、my_list.index(x) 也都是 O(n)，常被忽略。

名詞 先看懂這幾個詞

O(1)、O(n)（時間複雜度）
描述「資料變多時，工作量怎麼增加」。O(n)：資料多 10 倍，工作量約多 10 倍；O(1)：不管資料多少，工作量大致固定。不是實際秒數，而是成長的趨勢。
list 的內部結構
list 是一段連續的指標陣列，每格存的是「指向物件的參照」，物件本身散落在記憶體各處。所以 my_list[i] 能直接算出位置（O(1)），但要找「id 是 42 的物件」只能一格一格看。
dict（雜湊表，hash table）
把 key 丟進雜湊函式（hash()）算出一個數字，直接跳到對應的位置存取，所以查找、新增、刪除平均都是 O(1)。比喻：list 像一疊沒分類的名片，要一張張翻；dict 像依編號分好格的收納櫃。
可雜湊（hashable）
能當 dict key 的值：在生命週期內 hash() 不變，例如 int、str、tuple（內容也可雜湊時）。list、dict 這類可變物件不能當 key。
索引（index）dict
不是把資料搬走，而是另外建一個「key → 物件」的對照表。dict 存的也是參照，物件本身不會被複製一份。
collections.deque
雙端佇列，兩端新增 / 移除都是 O(1)。需要「從前面拿出來」的佇列時，用它取代 list。

解法 先建一次 dict 索引，之後用 key 查

users_by_id = {u.id: u for u in users}   # 建索引：O(n)，只做一次

for order in orders:
    user = users_by_id.get(order.user_id)   # 平均 O(1)；找不到回傳 None
    ...

總成本從約 n × m 變成 n + m。

同一個 key 對應多個物件時，用 defaultdict(list) 分組：

from collections import defaultdict

orders_by_user = defaultdict(list)       # 第一次用到某個 key 時自動建立空 list
for o in orders:
    orders_by_user[o.user_id].append(o)

orders_by_user.get(42, [])               # 用 .get 查詢才不會順手建立空的 key

從前面取出的佇列，用 deque：

from collections import deque

task_queue = deque()
task_queue.append("task-1")              # 右端加入：O(1)
task_queue.append("task-2")
next_task = task_queue.popleft()        # 左端取出：O(1)；list.pop(0) 是 O(n)

判斷 用 list 還是 dict

需求選擇
依某個 key（id、名稱）反覆查找 / 更新 / 刪除dict
只查一兩次、資料很少list 直接掃就好，建索引本身也要 O(n)
依位置存取、排序、切片、允許重複list
保持插入順序list 和 dict 都可以（dict 從 Python 3.7 起保證插入順序）
只想知道「有沒有出現過」set（同樣是雜湊，x in s 平均 O(1)）
先進先出佇列collections.deque；不要用 list.pop(0) / list.insert(0, x)

取捨 注意

  • dict 比 list 佔更多記憶體：雜湊表要保留空位才能維持 O(1)。
  • 索引要跟資料同步：同時保留 list 和 dict 時，新增 / 刪除都要兩邊一起改，否則會查到舊資料。只要「依 key 查 + 保持順序」，單一個 dict 就夠了（list(d.values()) 即依插入順序）。
  • key 重複時，{u.id: u for u in users} 只會留下最後一個，不會報錯；不確定是否唯一時要先檢查或用 defaultdict(list)。
  • O(1) 是「平均」：大量雜湊碰撞時會變慢，但對一般 int / str key 幾乎不用擔心。
更正原筆記：
  • 原筆記把 task_queue.pop(0) 當作「適合 list 的場景」。list.pop(0) 要把後面所有元素往前搬，是 O(n)；佇列應該用 collections.deque.popleft()（O(1)）。
  • 原筆記一邊寫 dict「無固定順序」，一邊寫「3.7+ 保證插入順序」，互相矛盾。正確是：Python 3.7 起 dict 保證保留插入順序（CPython 3.6 已是如此，但當時只是實作細節）。所以「需要維護順序就用 list」也不成立，「list + dict 混合」只在需要依位置存取或重新排序時才有必要。
  • 原筆記說 list 是「連續記憶體空間」，容易誤解成物件連續存放。實際上連續的是指標陣列，物件本身各自存在別處；dict 存的也是指標，所以建索引不會複製物件。
