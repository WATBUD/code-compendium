優化案例：互不相關的非同步指令改成同時執行

展開一個 branch 要依序跑 5 個 git 指令 · 結論：彼此不依賴的 await，用 Promise.all 同時發出

原因

for-each-ref→ 等 → rev-parse→ 等 → rev-list（未 push）→ 等 → rev-list（未 pull）→ 等 → git log 
// 原本：一個接一個 await，總時間 = 5 個指令時間相加
const ref      = await exec('git for-each-ref …')
await exec('git rev-parse --verify upstream')
const unpushed = await exec('git rev-list branch --not upstream')
const unpulled = await exec('git rev-list upstream --not branch')
const log      = await exec('git log branch upstream …')
  1. 後 3 個查詢不需要彼此的結果，卻排隊等前一個做完。
  2. 總耗時 = 每個指令時間相加，每多一個功能就多一份延遲。
  3. 展開多個 branch 或「搜尋 tag」時會一次載入全部，延遲被放大。

名詞 先看懂這幾個詞

非同步（async）與 await
執行 git 指令要花時間（要啟動行程、讀硬碟）。exec(...) 不會卡住程式，而是回傳一個 Promise（「承諾：做完會通知你」）。 await 的意思是：在這一行等它做完，再往下執行。
連續寫三個 await = 排隊：第一個做完才開始第二個。
依賴關係
B 需要 A 的結果 → 必須等 A 做完（有依賴，要排隊）。
B 和 C 彼此不看對方的結果 → 可以同時開始（沒依賴，可並行）。
做法：先畫出誰需要誰，沒有箭頭相連的就能一起跑。
Promise.all
把一組 Promise 同時啟動，全部做完才回傳結果陣列（順序和你傳入的順序一致）。總耗時 ≈ 最慢的那一個，而不是全部相加。 
// 序列：100 + 100 + 100 = 300ms
await a(); await b(); await c()

// 並行：max(100, 100, 100) ≈ 100ms
await Promise.all([a(), b(), c()])
注意：只要其中一個失敗，整個 Promise.all 就會失敗，其他的結果也拿不到。
Promise.allSettled
跟 Promise.all 一樣同時跑，但不管成敗都等全部結束，回傳每個的結果（成功或失敗）。適合「某個失敗不該影響其他」的情況。
upstream（上游分支）與 [gone]
本地 branch 通常對應一個遠端 branch（例如 feature/x ↔ origin/feature/x），那個遠端 branch 就叫它的 upstream。 如果遠端已經把它刪掉，git 會標成 [gone]。
rev-list A --not B
列出「在 A 裡、但不在 B 裡」的 commit。
branch --not upstream = 本地有、遠端沒有 = 還沒 push；
upstream --not branch = 遠端有、本地沒有 = 還沒 pull。

解法 分成「有依賴」與「無依賴」兩輪

先畫依賴：只有第 1 步的結果（upstream 名稱）被後面用到，後面 3 個彼此獨立 → 2 輪，第 2 輪同時跑

第 1 輪：for-each-ref→ 第 2 輪（同時）：git log ＋ rev-list 未 push ＋ rev-list 未 pull 
// 第 1 輪：一次拿到 是否本地 / upstream / upstream 是否已被遠端刪除
const { stdout } = await exec(
  'git for-each-ref --format="%(refname)|%(upstream:short)|%(upstream:track)" refs/heads/<branch>')
const [refname, up, track] = stdout.trim().split('|')
const upstream = up && !track.includes('gone') ? up : ''    // [gone] = 遠端已刪除，不必再 rev-parse 驗證

// 輔助標記失敗不該拖垮主清單：每個各自吞掉錯誤，回傳空集合
const markerSet = async (cmd) => {
  try { return toSet((await exec(cmd)).stdout) } catch { return new Set() }
}

// 第 2 輪：互不相關 → 同時執行
const [{ stdout: log }, unpushed, unpulled] = await Promise.all([
  exec(`git log ${revs} …`),                                                    // 主要資料：失敗要丟錯
  markerSet(`git rev-list ${branch} --not ${upstream || '--remotes'}`),          // 未 push
  upstream ? markerSet(`git rev-list ${upstream} --not ${branch}`) : Promise.resolve(new Set())  // 未 pull
])
兩個重點：
① 用 %(upstream:track) 取代額外的 rev-parse，少跑一個指令。
② git log 是主要資料，失敗就該丟錯；粉色 / 白色標記只是輔助，各自 try/catch 回傳空集合，失敗不會讓整個清單消失。

判斷

情況做法
B 需要 A 的結果保持順序：await A 再 B
B、C 都只需要 A 的結果，彼此無關A 之後 Promise.all([B, C])
某個失敗不能影響其他各自 try/catch，或用 Promise.allSettled
要同時跑的數量很多（幾十個以上）限制並行數，避免同時啟動太多行程互搶資源

這個案例只有 3 個並行指令，不需要限流。
