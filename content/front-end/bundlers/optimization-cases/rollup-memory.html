建置優化案例：Rollup 大型專案記憶體不足

建置時 JavaScript heap out of memory · 結論：先調高上限救急，再減少進入模組圖的內容

原因

大型專案 / monorepo 建置→bundler 把整個模組圖放進記憶體分析→分析越精細、模組越多越吃記憶體→Node heap 上限被打爆→JavaScript heap out of memory
FATAL ERROR: Ineffective mark-compacts near heap limit
Allocation failed - JavaScript heap out of memory
  1. 整張模組依賴圖都要裝進記憶體：模組、第三方套件、跨檔案引用越多，圖越大。
  2. Tree-shaking 追蹤得很細：Rollup 會分析每個變數、函式是否被使用，連未執行的邏輯都要判斷能不能刪，換來更精準的輸出，也吃更多記憶體。
  3. 分包策略較保守：多個動態載入共用的依賴可能被重複打包，monorepo 共用函式庫多時更明顯 → 圖更大、輸出也更大。
  4. Node 的 heap 上限：預設上限依 Node 版本與機器記憶體而異（常見約 2–4 GB），巨型建置容易碰到。
更正原筆記：原筆記把「一次載入整個模組圖」說成 Rollup 獨有。實際上各家 bundler（包含 webpack）都會在記憶體中建立完整模組圖；差別主要在分析的細緻程度與輸出策略，而不是「只有 Rollup 會一次全讀」。Vite 的正式建置底層用 Rollup，所以會遇到同樣的問題。

名詞 先看懂這幾個詞

模組圖（module graph）
從入口檔出發，順著 import 展開的整張「誰依賴誰」的圖。bundler 要先讀完整張圖才能決定怎麼打包。
Heap（堆積記憶體）與 --max-old-space-size
Node 存放物件的記憶體區域，有上限。--max-old-space-size=4096 把上限調成 4096 MB。
Monorepo
把多個套件 / 專案放在同一個 repo。共用函式庫會被很多地方引用，bundler 要分析的內容更多。

解法

① 暫時：提高 Node 記憶體上限（治標）

node --max-old-space-size=4096 node_modules/vite/bin/vite.js build

# 或用環境變數（對所有 node 子行程生效）
NODE_OPTIONS=--max-old-space-size=4096 npm run build

這只是把天花板墊高，根本問題（圖太大）還在。

② 治本方向：讓進入圖的東西變少

  • externalize 大型依賴：不要讓巨大的第三方套件進入分析（Rollup 的 external）。
  • 共用函式庫先各自建置（monorepo 先 build 套件，主專案引用產物而不是原始碼）。
  • 降低 sourcemap 成本：sourcemap 很吃記憶體，必要時關閉或只在需要的環境產生。
  • 拆成多個較小的 build，或升級 bundler 版本。
說明：原筆記只提供「暫時提高上限」這個解法；②是業界常見的緩解方向，效果依專案而異，請實測，並以 Node 的記憶體使用量（如 --trace-gc 或觀察峰值）確認有沒有改善。

判斷

情況做法
剛好踩到上限、要先讓 CI 過調高 --max-old-space-size（記得之後處理根因）
專案持續長大externalize、先建置共用套件、減少 sourcemap
輸出有重複依賴檢查動態 import 的共用模組，調整分包
