Android 優化案例：ABI Splitting 縮小 APK

通用 APK 內含所有 CPU 架構、體積過大 · 結論：依架構拆分，每台裝置只下載自己需要的

原因

APK 內含所有 CPU 架構的原生函式庫→一台手機只會用其中一種→APK 體積變大→下載慢、安裝慢、佔儲存空間
  1. 原生函式庫（.so）要每種 CPU 架構各一份：armeabi-v7a、arm64-v8a、x86、x86_64。
  2. 「通用 APK」把它們全部打包，但裝置實際只需要自己那一種，其餘都是浪費。

名詞 先看懂這幾個詞

ABI（Application Binary Interface）
對應「CPU 架構」。手機多為 arm64-v8a，舊手機 armeabi-v7a，模擬器常是 x86 / x86_64。原生程式碼要針對每個 ABI 各編譯一份。
原生函式庫（.so）
C / C++ 編譯出來的檔案（React Native 的 JS 引擎、圖片 / 加密函式庫等）。體積通常很大。
APK vs AAB
APK：可直接安裝的檔案。AAB（Android App Bundle）：上架 Google Play 的格式，由 Play 依使用者裝置自動產生並派送合適的 APK。
versionCode
每個 APK 的整數版本號。上傳多個 APK 時，每個 APK 的 versionCode 必須各自不同。

解法

① 上架 Google Play：用 AAB（最省事）

上傳 .aab，Play 會自動依裝置拆分，你不需要設定 ABI splits。

② 自行發佈：用 ABI Splits 產生多個 APK

// android/app/build.gradle，放在 android { } 內，與 defaultConfig、buildTypes 同層
splits {
    abi {
        enable true                                          // 啟用 ABI 拆分
        reset()                                              // 清掉預設的 ABI 清單
        include "armeabi-v7a", "arm64-v8a", "x86", "x86_64"   // 要產生哪些架構
        universalApk false                                   // 不產生「包含全部」的通用 APK
    }
}
# 執行 ./gradlew assembleRelease 後的輸出：每個 APK 只含自己架構的 .so
android/app/build/outputs/apk/release/
├── app-armeabi-v7a-release.apk
├── app-arm64-v8a-release.apk
├── app-x86-release.apk
└── app-x86_64-release.apk

③ 只打包需要的架構（單一 APK，較簡單）

defaultConfig {
    ndk { abiFilters "armeabi-v7a", "arm64-v8a" }      // 不含 x86，真機通常夠用
}
取捨：設了 universalApk false，不符合任何已列架構的裝置就沒有 APK 可裝。若要直接給人安裝檔（不經 Play），建議保留通用 APK 當備案。上傳多個 APK 到商店時，還要自己為每個 ABI 設定不同的 versionCode（常見做法是依架構加上偏移量）。

判斷

發佈方式建議
Google Play上傳 AAB，交給 Play 處理
自行發佈安裝檔、要小檔案ABI Splits（保留通用 APK 當備案）
想要一個檔案但縮小體積abiFilters 只留常用架構
