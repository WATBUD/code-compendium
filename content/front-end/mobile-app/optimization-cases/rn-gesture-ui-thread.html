React Native 優化案例：JS 執行緒忙碌時，手勢與動畫卡頓

資料載入或大量運算時，拖曳跟不上手指、動畫掉幀 · 結論：把手勢與動畫放到 UI 執行緒跑（Gesture Handler + Reanimated worklet），不要每一幀都經過 JS 執行緒

原因

手指移動（UI 執行緒收到觸控）→事件交給 JS 執行緒處理→JS 正忙，事件排隊→算出新位置再交回 UI→晚了好幾幀 / 掉幀
// 原本：用 PanResponder + setState 拖曳
const [x, setX] = useState(0)
const pan = PanResponder.create({
  onMoveShouldSetPanResponder: () => true,
  onPanResponderMove: (_, g) => setX(g.dx),     // 每次移動：JS 處理事件 + 重新渲染元件
})
return <View {...pan.panHandlers} style={{ transform: [{ translateX: x }] }} />
  1. PanResponder 與 onTouch* 的處理函式都在 JS 執行緒執行：觸控從 UI 執行緒進來，要等 JS 有空才處理。
  2. JS 是單執行緒：列表渲染、JSON 解析、業務邏輯、網路回應處理都和手勢搶同一條線，任何長任務都會讓手勢停住。
  3. 每次移動都 setState → React 重新渲染 → 把變更送到原生端，一幀要做的事太多，在 60 / 120Hz 螢幕上很難每幀都趕上。
更正原筆記：
  1. 原筆記用「JSON 序列化 → 透過 Bridge 非同步傳送 → 原生端反序列化」說明 JS 與 UI 的溝通成本，這是舊架構（Bridge）的描述。React Native 0.76 起預設啟用新架構：JS 透過 JSI 直接呼叫 C++，不再經過 JSON 序列化；渲染改由 Fabric 處理，Shadow Tree 與 Yoga 版面計算由 C++ 端負責，也可以同步呼叫。
  2. 但新架構沒有解決這個問題：少了序列化成本，由 JS 驅動的手勢與動畫仍然要 JS 執行緒每一幀都有空去跑程式。JS 被長任務卡住時，下一幀的位置就算不出來，照樣卡頓。這正是要把程式移到 UI 執行緒（worklet）的原因。

名詞 先看懂這幾個詞

JS 執行緒 / UI 執行緒
JS 執行緒跑你寫的 React 元件、狀態、業務邏輯，一次只能做一件事。UI 執行緒（主執行緒）負責接收觸控、繪製原生畫面。比喻：UI 執行緒是櫃台，JS 執行緒是後面唯一的廚師；客人每個動作都要問廚師，廚師在忙，櫃台就只能讓客人等。
Bridge / JSI / Fabric
Bridge：舊架構，JS 與原生之間用序列化訊息非同步溝通。JSI：新架構，JS 可直接持有並呼叫 C++ 物件。Fabric：新架構的渲染器。這些改善了「溝通」，但沒有讓 JS 執行緒變成多執行緒。
react-native-gesture-handler（RNGH）
用原生的手勢辨識系統處理觸控，支援拖曳、縮放、旋轉、手勢優先順序與同時辨識。手勢辨識本身在 UI 執行緒，配合 Reanimated 時，回呼也能在 UI 執行緒執行。
worklet
可以被搬到 UI 執行緒執行的小段 JS 函式（Reanimated 用 Babel 外掛處理）。在 worklet 裡更新動畫值，完全不經過 JS 執行緒，所以 JS 再忙，拖曳仍然跟手。
useSharedValue / useAnimatedStyle
shared value：兩個執行緒都能讀寫的值，改它的 .value 不會觸發 React 重新渲染。useAnimatedStyle：在 UI 執行緒根據 shared value 算出樣式，值一變就直接更新畫面。
runOnJS
worklet 裡要呼叫一般 JS 函式（例如 setState、送 API）時，必須用 runOnJS(fn)(args) 把它排回 JS 執行緒。較新版本的 worklets 套件提供新名稱（scheduleOnRN），請依你使用的版本查文件。

解法 Gesture Handler + Reanimated：整段在 UI 執行緒

手勢回呼與動畫樣式都是 worklet，每一幀都在 UI 執行緒完成，只在結束時通知 JS 一次。

import { Gesture, GestureDetector } from 'react-native-gesture-handler'
import Animated, { useSharedValue, useAnimatedStyle, withSpring, runOnJS } from 'react-native-reanimated'

function Draggable({ onDrop }) {
  const x = useSharedValue(0)                       // 不是 state：改它不會 re-render
  const startX = useSharedValue(0)

  const pan = Gesture.Pan()
    .onStart(() => { startX.value = x.value })        // 記下起點，下次拖曳從目前位置接著拖
    .onUpdate((e) => {
      x.value = startX.value + e.translationX        // worklet：在 UI 執行緒更新，不經過 JS
    })
    .onEnd(() => {
      x.value = withSpring(0)                         // 回彈動畫也在 UI 執行緒跑
      runOnJS(onDrop)()                               // 只有「放開」這一次需要回到 JS
    })

  const style = useAnimatedStyle(() => ({
    transform: [{ translateX: x.value }],            // UI 執行緒讀 shared value 直接套樣式
  }))

  return (
    <GestureDetector gesture={pan}>
      <Animated.View style={[{ width: 80, height: 80, backgroundColor: 'tomato' }, style]} />
    </GestureDetector>
  )
}

// App 最外層要包 GestureHandlerRootView，手勢才會生效
import { GestureHandlerRootView } from 'react-native-gesture-handler'
export default function App() {
  return <GestureHandlerRootView style={{ flex: 1 }}><Draggable onDrop={() => {}} /></GestureHandlerRootView>
}

安裝 Reanimated 後，RNGH 的手勢回呼會自動當成 worklet 在 UI 執行緒執行；若某個手勢要在 JS 執行，可加 .runOnJS(true)。Babel 外掛的設定依 Reanimated 版本而不同，請照官方安裝說明。

怎麼確認

  1. 開啟開發選單的 Perf Monitor，會分別顯示 UI 與 JS 的 FPS。
  2. 拖曳時故意讓 JS 忙（例如觸發大量資料處理），觀察：原本寫法拖曳會停住；worklet 寫法 JS FPS 掉了，UI FPS 和拖曳仍然順。
  3. 效果依裝置與負載而異，要在實機（最好是低階 Android）上量，模擬器與開發模式的數字不準。

判斷 該用哪個

情境做法
拖曳、滑動卡片、縮放、底部抽屜等「跟手」互動RNGH + Reanimated worklet
只是播放固定的淡入、位移動畫Reanimated，或 Animated 加 useNativeDriver: true（只支援 transform / opacity 等非版面屬性）
捲動連動效果（header 收合、視差）useAnimatedScrollHandler
手勢結束後要更新資料、導頁在 onEnd 用 runOnJS 呼叫一次
在 move 回呼裡每次 setState不要

取捨

  • worklet 不能直接呼叫一般 JS 函式或使用大部分第三方函式庫，要透過 runOnJS；捕捉到的外部變數是複製過去的，之後在 JS 改它 worklet 看不到。
  • worklet 跑在 UI 執行緒：在裡面做重運算，卡住的就換成 UI 執行緒（整個畫面都卡），worklet 裡只放算位置這類輕量邏輯。
  • 不要在 render 裡讀 sharedValue.value 來決定 JSX，它不會觸發重新渲染，畫面不會跟著變。
  • 多兩個原生相依套件、需要設定 Babel 外掛，除錯也比一般 JS 麻煩。
  • 這不會讓 JS 執行緒變快：JS 長任務本身（例如大量資料處理）仍要另外優化或分批。
