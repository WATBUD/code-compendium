瀏覽器優化案例：阻塞渲染的 CSS 與 JS（render-blocking resources）

白畫面很久、LCP 慢 · 結論：首屏需要的 CSS 越少越早到越好；JS 一律 defer / async，不要擋住 HTML 解析

原因

解析 HTML 遇到外部 CSS / 同步 script→CSS 沒到不繪製；script 沒跑完不繼續解析→首次繪製（FCP）延後→最大內容（LCP）更晚出現
<head>
  <link rel="stylesheet" href="/all.css">     <!-- 全站 CSS 一大包，首屏只用到一小部分，卻要整包下載完才繪製 -->
  <script src="/vendor.js"></script>          <!-- 同步 script：HTML 解析停在這裡，等下載 + 執行 -->
  <script src="/analytics.js"></script>       <!-- 第三方慢，整頁跟著等 -->
</head>
<body>
  <img src="/hero.webp">                         <!-- LCP 圖片：要等上面都處理完才被解析到 -->
</body>
  1. 外部 CSS 是 render-blocking：瀏覽器在 CSS 下載、解析完之前不會繪製，避免先畫出沒樣式的畫面。
  2. 沒有 async / defer 的 <script src> 是 parser-blocking：script 可能用 document.write() 或改 DOM，所以瀏覽器先停下解析，等它下載並執行完。
  3. 同步 script 還要等前面的 CSS：script 可能讀取樣式（例如 getComputedStyle），所以 CSS 慢 → script 晚執行 → 解析更晚恢復。
  4. LCP 圖片、字型如果只寫在 CSS 或 body 深處，被發現得太晚，下載也跟著晚。
更正原筆記：
  1. 原筆記的範例 <script src="example.js" defer>console.log(...)</script> 說「這段代碼會立即執行」—— 錯。有 src 時，標籤裡面的程式碼完全被忽略、不會執行。另外，defer / async 對沒有 src 的一般 inline script 無效（會立即執行），type="module" 的 inline script 例外。
  2. 「defer 不會影響 CRP」太絕對：defer 不擋解析與首次繪製，但 script 仍要下載、執行，DOMContentLoaded 會等它跑完，互動也要等它。
  3. 原筆記的延遲載入範例 <img src="placeholder.jpg" data-src="image.jpg" loading="lazy"> 混用了兩種做法：loading="lazy" 延遲的是 src（佔位圖），data-src 沒有 JS 處理就永遠不會載入。原生寫法直接 <img src="image.jpg" loading="lazy" width="..." height="...">；而且首屏的 LCP 圖片不要 lazy。
  4. media="print" onload 不是「等主要內容渲染完才載入」：瀏覽器照樣會立刻以低優先權下載，只是不擋繪製，載完後再套用。
  5. SEO 筆記中「LCP 最影響排名，其次 INP，再來 CLS」沒有出處：Google 把三項 Core Web Vitals 都列為頁面體驗訊號之一，沒有公開各自的權重，內容相關性仍是主要因素。

名詞 先看懂這幾個詞

關鍵渲染路徑（Critical Rendering Path，CRP）
瀏覽器從收到 HTML 到畫出第一個像素要走的步驟：
  1. 解析 HTML → DOM（頁面結構）
  2. 解析 CSS → CSSOM（每個元素的樣式）
  3. DOM + CSSOM → Render Tree（只含要顯示的元素，display: none 不在裡面）
  4. Layout：算出位置與大小
  5. Paint / Composite：畫出像素、合成圖層
擋住第 1 或第 2 步的資源，就會延後整條路徑。
render-blocking vs parser-blocking
render-blocking：HTML 可以繼續解析，但不能畫（外部 CSS）。parser-blocking：連 HTML 都停止解析（同步 script）。
FCP / LCP
FCP（First Contentful Paint）：第一個文字或圖片畫出來的時間。LCP（Largest Contentful Paint）：視窗內最大的圖片或文字區塊畫出來的時間，Google 建議 2.5 秒內為良好、超過 4 秒為差。
async / defer
都讓 script 邊解析 HTML 邊下載。差在什麼時候執行：async 下載完立刻執行（執行時會暫停解析、順序不保證）；defer 等 HTML 解析完才依文件順序執行。type="module" 預設就是 defer 的行為；用 JS 動態建立並插入的 <script> 預設就是 async。
preload
<link rel="preload"> 告訴瀏覽器「這個檔案等一下一定會用到，現在就先下載」，但不會套用 / 執行它。用在「藏在 CSS 裡、太晚才被發現」的關鍵資源（字型、LCP 圖片）。
media 屬性
<link rel="stylesheet" media="print"> 表示這份 CSS 只用於列印，目前畫面用不到，所以不擋繪製。把它在 onload 時改成 all，就變成「不擋繪製、載完再套用」的非同步 CSS。

解法 A script 一律 defer 或 async

需要 DOM、彼此有先後順序的用 defer；獨立、誰先跑都沒差的第三方用 async。

<head>
  <script src="/vendor.js" defer></script>       <!-- 依序執行：vendor 一定先於 app -->
  <script src="/app.js" defer></script>          <!-- 放 head 也不擋解析，還能更早開始下載 -->
  <script src="/analytics.js" async></script><!-- 不依賴其他 script 與 DOM -->
</head>
下載時繼續解析？何時執行順序
<script src>否，停下來等下載完立刻依文件順序
async是下載完立刻（執行時暫停解析）不保證
defer是HTML 解析完、DOMContentLoaded 之前依文件順序

解法 B 關鍵 CSS 內嵌，其餘非同步載入

首屏需要的少量樣式直接寫在 <style>，不用等網路；其他 CSS 改成不擋繪製。

<head>
  <style>
    /* 只放首屏需要的：版面骨架、標題、主圖尺寸 */
    body { margin: 0; font-family: system-ui, sans-serif; }
    .hero { aspect-ratio: 16 / 9; }
  </style>

  <!-- 其餘樣式：以 print 載入（不擋繪製），載完改成 all 套用 -->
  <link rel="stylesheet" href="/rest.css" media="print" onload="this.media='all'">
  <noscript><link rel="stylesheet" href="/rest.css"></noscript>   <!-- 關閉 JS 時的退路 -->
</head>

解法 C 讓 LCP 資源被早一點發現

LCP 圖片與首屏字型用 preload / fetchpriority 提前下載，不要等 CSS 解析到才開始。

<link rel="preload" href="/hero.webp" as="image" fetchpriority="high">
<link rel="preload" href="/fonts/main.woff2" as="font" type="font/woff2" crossorigin>
<!-- 字型 preload 一定要 crossorigin（即使同網域），不然會被下載兩次 -->

<img src="/hero.webp" width="1200" height="675" fetchpriority="high" alt="">
<!-- 首屏 LCP 圖片：不要 loading="lazy"；寫 width / height 預留空間避免 CLS -->

判斷 該用哪個

資源做法
自己的主程式、有順序依賴defer（或 type="module"）
分析、廣告、客服等獨立第三方async，或等 load 後再動態插入
首屏版面必要的樣式內嵌 <style>，保持很小
首屏以下、彈窗、其他頁面的樣式media="print" onload 非同步載入
只在列印 / 特定螢幕寬度用的 CSS加正確的 media（例如 media="(min-width: 1024px)"），不符合時不擋繪製
LCP 圖片、首屏字型preload + fetchpriority="high"
首屏以下的圖片loading="lazy"
在 <head> 放同步的第三方 script不要

取捨

  • 內嵌 CSS 不能被快取，每頁 HTML 都變大；只放首屏必要的，通常交給建置工具自動抽取，手動維護容易和正式 CSS 脫節。
  • 非同步 CSS 套用前，首屏以下的內容可能先以無樣式出現或跳動，所以首屏範圍要抓對。
  • onload="..." 是 inline 事件處理器，網站有嚴格 CSP（禁止 inline script）時會被擋。
  • async 執行順序不保證，有依賴關係的 script 用 async 會偶發性壞掉。
  • preload 太多會互相搶頻寬，反而拖慢真正關鍵的資源；preload 了卻沒用到，主控台會出警告。
  • 這些都是減少「等待」，實際效果要用 Lighthouse / DevTools Performance 量測，不要假設一定變快。
