React 優化案例：長清單分批渲染（變動高度）

展開 branch 一次掛上最多 1000 筆 commit · 結論：高度不固定時，用分批掛載 + content-visibility

原因

展開 branch→ 一次掛上最多 1000 個列→ 每列含多個子元件→ 掛載慢、之後每次重繪也慢 
// 原本：全部直接 map 出來
commits.map((c) => <CommitRow key={c.hash} commit={c} … />)   // 最多 1000 個
  1. 畫面一次只看得到幾十列，卻先把 1000 列都建出來。
  2. DOM 節點多 → 排版、繪製、記憶體都變重。
  3. 固定列高的「虛擬列表」（REMOTE 列表用的）不能直接套：commit 列有時一行、有時因標籤換行變兩三行，高度不固定，算不出第 N 列在哪。

名詞 先看懂這幾個詞

掛載（mount）
React 把元件真的建成 DOM 放到頁面上。掛得越多，建立、排版、繪製的成本越高。「只掛看得到的」就是這份優化的核心。
固定高度 vs 變動高度
每列一樣高 → 可以用數學算出「捲到 520px 就是第 20 列」，只畫那幾列（真正的虛擬列表）。
每列高度不一 → 算不出來，只能換個做法：先少掛一點，需要時再加。
哨兵元素（sentinel）
清單最底下放一個沒內容的小元素，它的唯一任務是「站崗」：當它被使用者捲到看得見時，就代表「快到底了，該多載入一批」。 就像排隊隊尾舉著「隊伍結束」的牌子：牌子出現在視線裡，就知道要補人了。

哨兵（40 / 1000）
綠框 = 使用者看得到的範圍（視窗）
黃色橫條 = 哨兵，放在已掛載的列的最後面
哨兵一進入綠框 → 觸發「再掛 40 列」→ 新列把哨兵往下推 → 哨兵又離開視窗，等下次再進來
IntersectionObserver
瀏覽器內建的「某元素有沒有進入畫面」偵測器。你告訴它要盯哪個元素，進出視窗時它會主動通知你（呼叫你的函式）。
為什麼不用 scroll 事件自己算？scroll 事件每捲一下就觸發，要自己量位置、很吃效能（正是前一個案例的問題）；IntersectionObserver 由瀏覽器在底層處理，只在「進入 / 離開」那一刻才通知。
rootMargin: '300px 0px'
把偵測範圍往外擴 300px（上下各 300px，左右 0）。哨兵還差 300px 才進入畫面時就先通知，所以新的列在使用者捲到之前就掛好了，不會看到空白等待。
slice(0, visibleCount)
只取清單的前 visibleCount 筆來畫。visibleCount 是 state：一開始 40，每次加 40，直到等於總數。資料 1000 筆都已經在記憶體裡，只是「畫」的數量被限制。

解法 A 分批掛載：捲到底才多掛一批

運作流程：

  1. 一開始 visibleCount = 40，只畫前 40 列，最後放一個哨兵。
  2. IntersectionObserver 盯著哨兵。
  3. 使用者往下捲，哨兵（加上 300px 的提早量）進入畫面 → 瀏覽器通知我們。
  4. 通知時 setVisibleCount(c + 40)，再多畫 40 列，哨兵被往下推。
  5. 重複，直到 visibleCount ≥ 總數，此時不再放哨兵，也不再偵測。
const INITIAL_COUNT = 40, CHUNK_SIZE = 40

function CommitList({ commits, ...rowProps }) {
  const [visibleCount, setVisibleCount] = useState(INITIAL_COUNT)   // 目前畫幾列
  const sentinelRef = useRef(null)                                  // 指向哨兵元素
  const hasMore = visibleCount < commits.length                    // 還有沒畫的嗎

  useEffect(() => {
    const el = sentinelRef.current
    if (!el || !hasMore) return                                     // 全畫完了就不用盯

    // 建立偵測器：哨兵「進入畫面」時執行這個函式
    const io = new IntersectionObserver((entries) => {
      if (entries.some((e) => e.isIntersecting))                    // isIntersecting = 現在看得到
        setVisibleCount((c) => Math.min(c + CHUNK_SIZE, commits.length))   // 多畫一批（不超過總數）
    }, { rootMargin: '300px 0px' })                              // 提早 300px 通知

    io.observe(el)                                                  // 開始盯哨兵
    return () => io.disconnect()                                    // 元件卸載 / 重新訂閱前停止盯
  }, [hasMore, commits.length, visibleCount])                       // 每掛完一批就重新訂閱

  return (<>
    {commits.slice(0, visibleCount).map((c) =>                      // 只畫前 visibleCount 筆
      <CommitRow key={c.hash} commit={c} {...rowProps} />)}
    {hasMore && <div ref={sentinelRef}>{visibleCount} / {commits.length}</div>}   // 哨兵
  </>)
}
為什麼依賴陣列要包含 visibleCount？
IntersectionObserver 只在「狀態改變（沒看到 → 看到）」時通知。如果新掛上 40 列之後，哨兵仍然在畫面內（例如螢幕很高、列很矮），狀態沒變就不會再通知，清單會卡住。 每掛完一批就重新訂閱，新的 observer 一開始會立刻回報「哨兵目前看不看得到」，看得到就會接著再載下一批。

解法 B content-visibility：已掛載但看不到的列不排版不繪製

解法 A 控制「掛幾個」；解法 B 讓已經掛上、但在視窗外的列變便宜。

.commitItem {
  content-visibility: auto;
  contain-intrinsic-size: auto 34px;
}
content-visibility: auto
告訴瀏覽器：「這個元素不在畫面內時，可以跳過它內部的排版與繪製」。捲到附近才真的畫。
代價：瀏覽器會對它套用「paint containment」，超出元素範圍的內容會被裁掉（例如伸到外面的陰影、光暈）。
contain-intrinsic-size: auto 34px
元素被跳過繪製時，瀏覽器不知道它多高，捲軸會亂跳。這行給一個預留高度 34px；前面的 auto 表示「一旦真的渲染過，就記住真實高度」，之後用真實高度，捲軸就穩了。
兩個一起用： A 減少掛載數量（React 與 DOM 的成本）；B 讓已掛載但在視窗外的列跳過排版與繪製（瀏覽器的成本）。

判斷

列高做法
固定真正的虛擬列表：只掛視窗內的列，捲動時換（REMOTE 列表）
不固定分批掛載 + content-visibility（本案例）
不固定、且上萬筆需量測高度的虛擬列表套件（如 react-window 的可變高度版本）
取捨（誠實說明）：這不是嚴格的虛擬化——已經掛上的列不會在捲走後卸載，捲得越深記憶體越多。 content-visibility: auto 的 paint containment 會裁掉列邊界外的內容，使用前要確認列的視覺效果（陰影、光暈）都在邊界內。
