React 優化案例：列表 key 的正確用法

列表更新時多餘的重建或狀態錯位 · 結論：key 要用資料的唯一、穩定 id

原因

列表沒有 key / 用 index / 用 Math.random()→React 認不出「哪一項是哪一項」→多做不必要的更新或重建→效能差，甚至狀態錯位
items.map((item, i) => <li key={i}>{item.name}</li>)              // 用 index 當 key
items.map((item)    => <li key={Math.random()}>{item.name}</li>)  // 每次都是新 key
items.map((item)    => <li>{item.name}</li>)                              // 沒給 key（會有警告）
  1. Math.random()：每次重繪 key 都不同，React 認為每一項都是新的，全部卸載再重建（連輸入框內容、焦點都會消失）。
  2. index：在列表開頭插入 / 刪除 / 排序時，同一個 index 對到的資料變了，React 以為是「同一項換了內容」，就會逐項更新，甚至把狀態留在錯的項目上。
  3. 沒給 key：React 會退回使用 index 並警告，等於上一條。
更正原筆記：「沒有 key 就會重新渲染整個列表」不精確。沒有 key 時 React 是用位置（index）比對，問題在於開頭插入 / 重排時會每一項都被當成內容改變；而不是整個列表被重建。

名詞 先看懂這幾個詞

key
寫在列表項目上的「身分證」。React 靠它判斷「這一項上次就存在、只是更新」或「這是新的 / 已被移除」。
Diff（協調，reconciliation）
React 比較新舊兩份畫面描述，找出最少的更新。同一層的項目會先看 key 與元件類型：兩者都相同 → 視為同一個，只更新屬性；不同 → 卸載舊的、建立新的。
元件狀態跟著 key 走
input 的輸入內容、元件內部 useState 都「附著」在對應的項目上。key 對錯項目，狀態就會跑到別項去。

解法 

// 用資料本身「唯一且穩定」的 id
items.map((item) => <li key={item.id}>{item.name}</li>)
key 的三個條件：① 唯一（同一個列表內不重複）② 穩定（同一筆資料每次都一樣，不要在 render 裡產生）③ 跟資料綁定（用資料 id，不是位置）。
// 沒有 id 時：在資料「產生時」補一個，而不是在 render 時
const withId = rows.map((r) => ({ ...r, id: crypto.randomUUID() }))   // 只在載入資料時做一次

判斷

情況能用 index 當 key 嗎
列表會新增 / 刪除 / 排序、項目有狀態或輸入框不行，用資料 id
列表固定不變、純顯示、沒有狀態可以（影響不大）
任何情況用 Math.random() / Date.now()不行，每次重繪都全部重建
