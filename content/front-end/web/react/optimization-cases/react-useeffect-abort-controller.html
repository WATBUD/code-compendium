React 優化案例：useEffect 請求競態與 AbortController

舊請求晚回來蓋掉新資料 · 結論：effect 清理時 abort 上一個請求，並略過 AbortError

原因

使用者快速切換條件（id / 搜尋字 / 分頁）→連續發出多個請求→回來的順序不一定→舊請求晚回來 → 蓋掉新資料（競態）
useEffect(() => {
  fetch(`/api/user/${id}`)
    .then((r) => r.json())
    .then((data) => setUser(data))       // 不管這是不是「最新那次」的請求，回來就寫入
}, [id])
// id: 1 → 2 → 3，請求 1 最慢，最後才回來 → 畫面顯示的是 1 的資料，但目前選的是 3
  1. 競態（race condition）：請求回來的順序不等於發出的順序，慢的舊請求會覆蓋新結果。
  2. 元件卸載、條件已經改變，請求還在跑，浪費頻寬，回來還會去更新已經不需要的 state。

名詞 先看懂這幾個詞

AbortController / signal
瀏覽器內建，用來「取消尚未完成的非同步操作」。controller.signal 交給 fetch，之後呼叫 controller.abort() 就能中止該請求。
AbortError
請求被 abort 時，fetch 會丟出名稱為 AbortError 的錯誤。這是「我們主動取消」，不是真正的錯誤，要略過。
effect 清理函式（cleanup）
useEffect 回傳的函式。下一次 effect 執行之前、或元件卸載時會先執行它。這正好是「取消上一個請求」的時機。
競態（race condition）
結果取決於兩件事「誰先完成」，而這個順序不可控。

解法 在 effect 裡建立 controller，清理時 abort

useEffect(() => {
  const controller = new AbortController()          // 每次 effect 一個新的（不可重複使用）

  async function load() {
    try {
      const res = await fetch(`/api/user/${id}`, { signal: controller.signal })
      setUser(await res.json())
    } catch (err) {
      if (err.name === 'AbortError') return               // 主動取消，不是錯誤
      setError(err)
    } finally {
      if (!controller.signal.aborted) setLoading(false)   // 已被取消的請求不要動 loading
    }
  }
  setLoading(true)
  load()

  return () => controller.abort()                        // id 改變 / 卸載時，取消上一個請求
}, [id])
更正原筆記：原筆記的 finally { setLoading(false) } 對「被取消的請求」也會執行：舊請求被取消後，它的 finally 會在新請求還在進行時把 loading 設回 false。上面的寫法用 signal.aborted 擋掉。

判斷

情況做法
effect 內發請求，依賴會變一定要在清理函式 abort
多個請求同時進行每個請求各用一個 controller（abort 後不能再用）
不能取消的非同步（沒有 signal 的函式）用區域旗標 let ignore = false，清理時設 true，回來時 if (!ignore) 才寫入
要快取、重試、去重改用資料請求庫（React Query / SWR / RTK Query），它們已處理好

注意：開發模式的 StrictMode 會刻意把 effect 執行兩次（掛載 → 清理 → 再掛載），所以你會看到第一個請求被取消，這是正常的，不是 bug。
