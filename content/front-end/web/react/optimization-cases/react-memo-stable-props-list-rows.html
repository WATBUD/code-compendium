React 優化案例：列元件 React.memo + 穩定參照

父元件一重繪，上千個子列跟著重繪 · 結論：memo 只有在 props 穩定時才有用

原因

父元件重繪（任何 state / props 變化）→ 每個子列都被重新執行→ 每列新建 onClick / style 物件→ 子元件再往下全部比對→ 列越多越慢 
// 原本：列直接寫在父元件的 map 裡，每次重繪都要重做
commits.map((commit) => (
  <div
    onClick={() => { hideTip(); handleView(commit) }}      // 每次都是新函式
    onContextMenu={(e) => handleContextMenu(e, 'commit', commit)}
    style={{ cursor: 'pointer', ...indentStyle(depth) }}      // 每次都是新物件
  >…</div>
))
  1. 列不是獨立元件 → 沒有「props 沒變就跳過」的機會。
  2. 每列都建立新的函式與物件，就算內容一樣，「參照」也不同。
  3. 預設參數 = [] 每次是新陣列，會讓整排 memo 失效。

名詞 先看懂這幾個詞

重繪（re-render）
React 重新執行元件函式，產生新的畫面描述，再跟上一次比對、更新有差異的 DOM。執行函式本身就有成本，即使最後 DOM 沒變也一樣。父元件重繪時，預設所有子元件都會跟著重繪。
參照（reference）vs 值
數字、字串比的是「值」：3 === 3 為 true。
函式、物件、陣列比的是「是不是同一個東西」（記憶體位置）： 
() => {} === () => {}     // false，兩個內容一樣，但是兩個不同的函式
[] === []                 // false
const f = () => {}; f === f   // true，同一個
元件每次重繪都會重新執行函式內容，裡面寫的 () => …、{…}、[] 每次都是全新的，所以參照每次都變。
React.memo
把元件包起來，告訴 React：「props 沒有變就別重繪我」。
怎麼判斷「沒變」？用淺比較（shallow compare）：逐個 prop 用 === 比對上一次。
淺比較為什麼是關鍵
只要有任何一個 prop 每次都是新的函式 / 物件 / 陣列，淺比較就判定「有變」→ memo 白包了。所以「讓 props 保持同一個參照」比「加 memo」更重要，這就是下面說的穩定參照。
useCallback / useMemo
讓函式（useCallback）或計算結果（useMemo）在依賴沒變時，重繪後還是同一個參照。
只有要傳給 memo 子元件的值才需要，其他地方不必到處加。
用 ref 讀「最新值」
useRef 存的東西改了不會觸發重繪，而且 ref 本身永遠是同一個參照。把會常變的資料放進 ref，函式裡讀 ref.current，函式的依賴陣列就能保持空的，函式身分永遠不變。

解法 拆成 CommitRow + React.memo

props 沒變 → 這一列完全不重繪。每列自己用 commit 建立事件處理，父元件不用為每列產生新函式。

const CommitRowImpl = ({ commit, branch, depth, onView, onContextMenu, onTipHide, … }) => {
  // 這個函式「只在這一列重繪時」才重建；列用到的 commit 不變就不會重建
  const handleClick = useCallback(() => { onTipHide(); onView(commit) }, [onTipHide, onView, commit])
  const handleContextMenu = useCallback(
    (e) => { onTipHide(); onContextMenu(e, 'commit', commit) },
    [onTipHide, onContextMenu, commit]
  )
  return <div onClick={handleClick} onContextMenu={handleContextMenu}>…</div>
}

export const CommitRow = React.memo(CommitRowImpl)      // props 淺比較沒變 → 跳過重繪

這裡的設計：父元件只傳「所有列共用的、穩定的函式」，每一列需要的 () => handle(commit) 由列自己用 commit 組出來。

關鍵 讓傳進去的 props 穩定

逐個檢查「傳給 memo 元件的每一個 prop」，每個都要是同一個參照：

prop 的類型容易出的錯做法
共用函式內聯 () => …；依賴常變的 useCallbackuseCallback，依賴盡量少；常變的資料改用 ref 讀
可選的陣列 / 物件預設值 = []、|| [] 每次都是新的模組層級常數當預設值
資料物件每次重繪都重新 .map / .filter 出新物件用 useMemo，或直接傳 state / Redux 裡的原物件
 
// 1) 函式：用 ref 讀最新資料，依賴陣列保持為空
const branchesRef = useRef(branches)
branchesRef.current = branches
const handleContextMenu = useCallback((e, type, target) => {
  /* 需要 branches 時讀 branchesRef.current */
}, [])                                          // 依賴為空 → 這個函式永遠是同一個

// 2) 可選陣列：預設值不要寫 = []
const EMPTY_LIST = []                           // 模組層級，只建立一次
({ localOnlyTags = EMPTY_LIST, … }) => …

// 3) 資料：commit 來自 state，重新載入前參照不變
<CommitRow commit={commit} … />

判斷

  • 列數多、父元件又常重繪 → 拆列 + memo
  • 傳給 memo 元件的 prop 是內聯 () => …、{…}、[] → memo 無效，要先穩定它
  • 只有「要傳給 memo 子元件」的函式才需要 useCallback，其他不用
  • 列很少、父元件很少重繪 → 不必加，memo 本身也要花比對的成本
怎麼確認有效：用 React DevTools 的 Profiler，勾選「Record why each component rendered」。memo 生效時，沒變的列會顯示「Did not render」；仍然重繪的列會告訴你是哪個 prop 變了，就是下一個要穩定的對象。
