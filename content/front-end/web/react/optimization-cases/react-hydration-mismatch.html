React 優化案例：Hydration mismatch（伺服器與客戶端輸出不一致）

主控台出現 hydration 錯誤、某段內容被整段換掉 · 結論：第一次渲染要跟伺服器輸出一模一樣；會變的內容等 mount 之後再算

原因

伺服器渲染出 HTML（值 A）→瀏覽器 hydrate 時再跑一次元件（值 B）→A ≠ B→React 報 mismatch，改用客戶端重新渲染該區塊
// 原本：第一次渲染就用「每次執行結果都不同」的值
function Clock() {
  return <p>現在時間：{new Date().toLocaleTimeString()}</p>   // 伺服器與瀏覽器的「現在」不同，時區也可能不同
}

function Card() {
  const id = Math.random()                                // 兩邊各抽一次，必然不同
  return <label htmlFor={'f' + id}>名稱</label>
}

function Price({ n }) {
  return <span>{n.toLocaleString()}</span>                  // 伺服器用 Node 的預設語系，瀏覽器用使用者的
}

function ThemeLabel() {
  const dark = typeof window !== 'undefined' && localStorage.theme === 'dark'
  return <span>{dark ? '深色' : '淺色'}</span>                // 伺服器永遠走「淺色」分支
}
  1. Hydration 時 React 會在瀏覽器再執行一次元件，並假設結果和伺服器送來的 HTML 完全相同。
  2. 時間、亂數、語系 / 時區格式化、typeof window 或 localStorage 分支，都會讓兩邊的第一次渲染結果不同。
  3. 不一致時（React 18 起）React 會丟掉這段伺服器 HTML，改在客戶端重新渲染（範圍到最近的 <Suspense> 邊界，沒有就是整個 root），開發模式會印出錯誤。SSR 的好處在那一段就沒了，還多做一次渲染。
更正原筆記：
  1. 原筆記把 mismatch 稱為「畫面閃爍」。mismatch 是 React 比對結果不一致的錯誤 / 警告；內容被換掉而跳一下只是可能的後果之一，兩者不是同一件事。
  2. 原筆記把「客戶端 useEffect 在 Hydration 後改變內容」列為成因 —— 這不會造成 mismatch。useEffect 在 hydration 完成之後才執行，此時比對已經結束；這反而是下面的解法。
  3. 原筆記說 React Server Components 是「未來支援」。Next.js App Router 在 13.4 起已標為 stable，Server Components 是預設，現在就能用。

名詞 先看懂這幾個詞

Hydration
伺服器先送來「已經長好的 HTML」，瀏覽器載入 JS 後，React 不重建 DOM，而是沿用現有 DOM、綁上事件與 state，讓頁面變成可互動。比喻：伺服器送來組好的家具，React 只負責接上電源，所以它必須確認家具跟說明書一模一樣。
Hydration mismatch
React 在 hydrate 時算出來的內容（文字、屬性、結構）和伺服器 HTML 不一樣。常見訊息如「Text content does not match server-rendered HTML」或「Hydration failed because the server rendered text didn't match the client」（依 React 版本而異）。
useEffect 的執行時機
useEffect 只在瀏覽器、而且在畫面 commit 之後才執行，伺服器渲染時完全不跑。所以「放在 useEffect 裡才算的值」不會出現在第一次渲染，兩邊自然一致。
suppressHydrationWarning
加在單一元素上的屬性，告訴 React「這個元素的文字 / 屬性兩邊本來就會不同，別報錯」。只壓警告、只作用一層，React 不會幫你把文字修成客戶端的值。
useId
React 18 的 Hook，產生在伺服器與客戶端保證相同的 id，用來取代 Math.random() 產生的 id（例如 htmlFor、aria-describedby）。

解法 A 讓兩邊輸出一致

值在伺服器決定好、當資料傳下去；格式化時固定語系與時區；id 用 useId。

// 時間：用資料裡的固定時間點，並固定 locale 與 timeZone
const fmt = new Intl.DateTimeFormat('zh-TW', {
  timeZone: 'Asia/Taipei',                  // 不固定的話，伺服器（常是 UTC）和使用者時區會算出不同字串
  dateStyle: 'medium', timeStyle: 'short',
})
function PostTime({ createdAt }) {             // createdAt 來自資料，伺服器與客戶端拿到同一個值
  return <time dateTime={createdAt}>{fmt.format(new Date(createdAt))}</time>
}

// 數字：一樣指定語系
const price = n.toLocaleString('zh-TW')

// id：兩邊相同
function Card() {
  const id = useId()
  return <><label htmlFor={id}>名稱</label><input id={id} /></>
}

解法 B 只屬於瀏覽器的內容，mount 之後再渲染

第一次渲染輸出兩邊都一樣的佔位，真正的值在 useEffect 裡才算。

function Clock() {
  const [now, setNow] = useState(null)            // 伺服器與 hydrate 時都是 null → 一致
  useEffect(() => {
    setNow(new Date())                              // 只在瀏覽器、hydration 之後才執行
    const t = setInterval(() => setNow(new Date()), 1000)
    return () => clearInterval(t)                     // 卸載時清掉計時器
  }, [])
  return <p>現在時間：{now ? now.toLocaleTimeString() : '--:--:--'}</p>
}

function ThemeLabel() {
  const [dark, setDark] = useState(false)             // 先用伺服器也會得到的預設值
  useEffect(() => { setDark(localStorage.theme === 'dark') }, [])  // mount 後才讀 localStorage
  return <span>{dark ? '深色' : '淺色'}</span>
}

整個元件都只能在瀏覽器跑（例如地圖、依賴 window 的套件）時，Next.js 可用 dynamic(() => import('./Map'), { ssr: false }) 跳過伺服器渲染；App Router 中這個寫法要放在 Client Component（'use client'）裡。

解法 C 無法避免的單一文字：suppressHydrationWarning

像「依使用者時區顯示的時間戳」這種本來就該不同、又只是一段文字的情況，可以只壓掉那一個元素的警告。

<time dateTime={iso} suppressHydrationWarning>    // 只對這個元素本身的文字 / 屬性有效，不影響子元素
  {new Date(iso).toLocaleString()}
</time>

判斷 該用哪個

情境用原因
文章時間、價格、數字格式A 固定 locale / timeZone可以讓兩邊一致，SEO 也拿得到內容
元素 id（label、aria）A useId專門為 SSR 設計
倒數、時鐘、「3 分鐘前」、讀 localStorage / 視窗大小B mount 後再算伺服器根本不知道正確值
只能在瀏覽器跑的整個元件B dynamic + ssr: false不在伺服器渲染就不會不一致
單一元素、文字本來就該不同C suppressHydrationWarning最後手段，範圍要小
用 typeof window 在 render 裡分支不要這正是 mismatch 的典型來源

取捨

  • 解法 B 的內容要等 JS 載入、hydrate 完才出現：搜尋引擎與首屏看到的是佔位；佔位要預留尺寸，不然會造成版面位移（CLS）。
  • suppressHydrationWarning 只是不報錯，畫面會保留伺服器的文字直到下次更新；到處加會把真正的 bug 一起藏起來。
  • 瀏覽器擴充功能（翻譯、密碼管理器）改動 DOM 也會觸發 mismatch 訊息，這類不是你的程式錯，排查時先用無痕視窗確認。
